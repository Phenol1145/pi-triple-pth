## 0. 理论层：五节理论 + 三节应用综合 + 一个猜想 + 一个方法

> 2026-08-13 用户总结——PTH 一切设计的理论根基。本节先于概念：后续 6 域概念全部标注"是哪条命题的推论"。

### 0.1 三个命题

**命题 1——思考量分摊**：复杂任务的思考总量不消失，但可以分解到多个专职角色——每个角色只思考它那份窄问题，不做全盘推演。

**命题 2——记忆量分摊**：模型的"记忆"（上下文窗口）是稀缺资源——长期知识外置到共享记忆库（memory / role-doc / capability-index）——模型不记，用的时候查——每个任务的上下文只装当前任务所需的最小知识。

**命题 3——专注度是核心**：模型智力输出质量 ≈ 智力水平 × 专注度。专注度被上下文噪声侵蚀（无关工具描述、无关历史、无关空间）——一切裁剪机制（最小工具面 / pick_tools / 描述场景化 / 渐进降输入）的本质不是省 token——是**保专注度**。

### 0.2 推论：高低智力分层

专注度足够高的窄任务，低智力模型（flash）产出 ≈ 高智力模型（pro）——而 **flash 的输出速度是 pro 不能及的**（几十 vs 几 tok/s 量级）。

因此：**"pro 想一次（规划/裁决）+ flash 干多次（执行族）"**——总成本 ≈ 用 pro 干所有事的一小部分。

### 0.3 推论：智力代偿理论〔争议〕（2026-08-14 用户）

> 工具调用、PTC 模式、agentic-JIT 优化，本质上在做同一件事：**用机械化方法、传统算法或低成本模型，代偿 LLM 的部分智力负担**。
>
> **〔争议〕2026-08-14 用户裁定**：本理论整体标注为争议条目——代偿有串联、并联两种接法，状态不同：
> - **串联代偿〔已立〕**：代偿器接在 LLM 思考链上，每步仍由 LLM 触发/编排——工具调用、PTC 临时工具属此类，已较好实现（0.6 实验证据）；
> - **并联代偿〔待议〕**：代偿器旁路 LLM、并接原始系统，直接接管部分功能——同类任务由固化工具直接完成、LLM 不进入该环节。**可实现性待议**（详见 0.3.6）。

#### 0.3.1 视角翻转：从「调用工具」到「制造工具」

| | 旧视角 | 新视角（智力代偿） |
|---|---|---|
| LLM 的角色 | 工具的使用者——任务全程由 LLM 亲自完成，工具只是手 | 工具的制造者——LLM 制造工具，工具**代替它直接完成部分工作**〔待议——并联代偿〕 |
| 工具的定位 | 被动的能力扩展（读取/执行/搜索） | 外置的确定性智力——把「这一部分思考」固化为机器执行 |
| 代偿对象 | —— | LLM 的部分智力负担（重复推理/机械步骤/确定性计算） |

#### 0.3.2 代偿阶梯（三个实例——同一件事的三级形态）

1. **工具调用（单步代偿）**：bash 计算、SQL 查询、文件操作——每一步都是机械化方法代偿一次思考；确定性执行，零 token 重复。
2. **PTC 模式（制造临时工具）**：LLM 写一段 ts 程序编排多步——程序 = LLM 制造的**临时工具**，代替 LLM 亲自分步执行；变量/循环/复用由语言机制代偿，LLM 只付一次「设计费」。
3. **agentic-JIT（制造持久工具）**：把反复出现的模式固化为规则/技能（optimizer-hotspots 规则 stamp、skill 类型 §10 N2）——后续任务由固化工具直接代偿，LLM 不再重复思考同类问题〔待议——并联代偿，见 0.3.6〕。**JIT 的 collect→propose→apply→verify 环 = 「LLM 制造工具」的生产线。**

#### 0.3.3 与三个命题的咬合

- 代偿是命题 1（思考量分摊）的**工具化终极形态**：分摊出去的思考不只交给别的角色，还交给机器与程序；
- 代偿是命题 2（记忆量分摊）的**执行侧同构**：记忆外置是「知识代偿」，工具固化是「能力代偿」；
- 0.2 高低智力分层是代偿的**特例**：低成本模型（flash）= 代偿梯队中的「低智力代偿器」——「pro 想一次 + flash 干多次」就是「高智力制造、低智力执行」。

#### 0.3.4 代偿边界（设计必须承认）

- **不可代偿区**：需要全局视野的深度推理不可代偿（与 0.4 边界条件 2 同构）——planner/controller 保持 pro；
- **过度代偿有害**：让 LLM 花智力管理工具面 = 代偿倒退（T3 废弃 pick_tools 即此教训——动态工具注入让 LLM 为「选择工具」付智力成本，违背代偿初衷）；
- **代偿产物需要质检**：固化工具同样会出错——deopt 回滚（0.7.2）+ 审批面 A/B/C = 代偿产物的质检线。

#### 0.3.5 理论 → 机制映射

| 代偿机制 | PTH 落点 |
|---|---|
| 机械化方法/传统算法 | bash/python/ts 核 · SQL（memory.query）· 确定性执行 |
| 低成本模型 | flash 执行族（推理档 low/medium——scout/developer/tester 等） |
| 临时工具（PTC） | ts.run 程序模式 · 能力函数组合 |
| 持久工具（agentic-JIT）〔待议〕 | optimizer-hotspots 规则固化 · skill 类型（N2）· 角色分化 |
| 代偿产物质检 | deopt 回滚 · 审批面 A/B/C · 负结果收敛 |

#### 0.3.6 争议裁定：串联代偿已立，并联代偿待议（2026-08-14 用户）

- **串联代偿〔已立〕**：代偿器接在 LLM 思考链上——LLM 仍主导流程，每步由 LLM 触发与编排。工具调用（单步代偿）、PTC 临时工具（程序代偿编排）皆属此类，已较好实现——0.6 实验证据（memory-stats 13→2 步、cacheRead 82.6%、flash 37 任务/973 步）。
- **并联代偿〔待议〕**：代偿器旁路 LLM、并接原始系统，**直接接管部分功能**——同类任务不再经过 LLM，由固化工具（规则/skill/程序）直接完成。可实现性待议：
  - 当前 agentic-JIT 产物（optimizer 规则）仍是**提示侧串联代偿**——规则注入 prompt，LLM 仍要读、判断、执行，并未真正旁路 LLM；
  - 真正并联需任务路由层识别「已固化类任务」并直接走固化路径（LLM 最多只做质检）——无实测证据，属开放问题（关联 §10 N2 skill 生态转化）。
- **引用规则**：凡引用 0.3——串联部分按已立结论引用；并联部分必须带〔待议〕；0.3.1 表格与 0.3.2 第三级的并联主张不得作为已实现事实引用。

### 0.4 两个边界条件（设计必须承认）

**边界 1——协调成本**：分摊不是免费的——路由、交接、worker-index 都是开销。**最优分摊粒度存在**：任务太碎→协调成本吞掉节省；任务太整→负担回到一人。
→ **controller 裁决分化/合并（"任务分化优先于 worker 分化"）正是这个平衡的调节器。**

**边界 2——可分性条件**：不可分解的任务（需要全局视野的深度推理）强行分给 flash 反而更差。
→ 所以 planner/controller 保持 pro——理论不要求"一切下沉"，要求**"可分的下沉"**。

### 0.7 优化理论：控制理论 × 现代 JIT

> 第二个理论根基（2026-08-13 用户）——回答"系统怎么变好"。
> 心智负担理论回答"怎么便宜地干活"；优化理论回答"怎么让系统持续变便宜"。

#### 0.7.1 控制论映射：sensor → controller → actuator 反馈回路

经典负反馈回路 → PTH 角色分化：

| 控制论角色 | 职责 | PTH 落点 |
|---|---|---|
| **传感器（sensor）** | 测量系统状态 | sensor 族（worker-opt / system-opt / memory / resource）——obs.callpoint 上报 + scorecard 聚合快照 |
| **控制器（controller）** | 比较设定值与实测——计算控制量 | controller 族×5——裁决 official / reject / merge |
| **执行器（actuator）** | 控制量作用于系统 | actuator——把 official 提案落为实际修改（代码/参数/角色注册） |
| **设定值（setpoint）** | 期望状态 | 优化目标：步数↓ 失败率↓ 成本↓ 时间复用率↑ |
| **人在回路（supervisor）** | 防控制器失控 | 审批面 A/B/C——控制量不自动生效 |

**关键：负反馈而非开环**——每次调节后必观测复测（apply → verify 窗口）——偏差驱动调节，而非一次调好。

#### 0.7.2 现代 JIT 思想：按需优化 + 回退保护

现代 JIT（profiling → 热点识别 → 按需编译 → 失效回退）→ PTH 优化管线：

| JIT 概念 | PTH 落点 |
|---|---|
| profiling（画像） | scorecard 聚合快照（审批面 B——原子 upsert） |
| 热点识别（hotspot） | 反模式检测（repeated-fail / no-progress / gate-heavy / token-bloat） |
| 按需优化（不是全量预调） | 有观测证据才 propose——不预先调优 |
| 回退（deopt） | 劣化 50%+ 自动撤销（baseline 对比 + rolled_back 标记） |
| 版本化 | baseline 记于提案 meta——对比依据 |

**JIT 的精髓：优化是局部、证据驱动、可撤销的——与"全量预设计"相对。**

#### 0.7.3 多级优化循环（不同步长——时间尺度分离）

```
环 4 · 资源环（日/重启级）   resource-sensor → controller:resource → 资源调参（batch/核池/模型配比）
环 3 · 控制环（批次/小时级） sensor 聚合 → controller 裁决 → 审批面 → actuator 应用
环 2 · JIT 环（任务/分钟级）  optimizer-loop：collect → propose → apply → verify（+deopt）
环 1 · 防护环（单步/秒级）    agent-loop：负结果收敛 / 参数指纹 / 未知工具引导（执行内制动）
```

时间尺度分离原则（多环控制的核心）：**快环调微变（工具面/引导），慢环调大变（角色/资源）**——环间不互相干扰，防振荡。

#### 0.7.4 稳定性设计（控制论的贡献）

- **增益限制**：每窗口一个提案——调节幅度受限——不激进
- **复测验证**：apply 后 verify 窗口确认改善才保留——闭环负反馈
- **振荡防护**：deopt 50% 阈值 + rolled_back 标记——同一优化不反复尝试（防 ping-pong）
- **人在回路**：审批面 A/B/C——控制器不能无限自动
- **洞察污染防线**：观测断言与注册表核对——传感器测不准的拒绝入库

#### 0.7.5 理论 → 机制映射

| 理论 | 机制 |
|---|---|
| 控制论 | sensor/controller/actuator 分化 · 审批面 · 负反馈复测（verify 窗口） |
| JIT | scorecard 聚合画像 · 反模式热点 · 按需 propose · deopt 回退 · baseline 版本化 |
| 多级循环 | 4 环步长分层（防护/JIT/控制/资源）· 时间尺度分离 |

### 0.8 LLM 注意力特征（API 协议面）

> 第三个理论根基（2026-08-13 用户）——回答"上下文怎么编排才让模型真正专注"。
> 前两个理论回答"怎么拆"与"怎么变好"；本节回答"每一份上下文怎么用出最大专注度"。

#### 0.8.1 位置效应：核心区寸土寸金

completion 模式 API 调用结构：system prompt / tool definitions / 消息序列（user/assistant/tool）。

**LLM 注意力分布不均匀**：

```
高注意力：system prompt · tool definitions · 会话开头（任务指令）· 会话结尾（最新状态）
低注意力：会话中间（历史消息——lost in the middle）
```

**核心区（开头+结尾）寸土寸金**——每一个 token 都是最高杠杆：决定模型"知道自己是谁、能用什么、要干什么、现在到哪了"。

**让 LLM 专注 = 有效编排核心区信息**——无关内容不进核心区，历史沉在中间。

#### 0.8.2 缓存命中率约束（编排的第二个目标）

前缀缓存（prompt cache）：**前缀稳定才能命中**——编排核心区必须同时优化两个目标：

1. **专注度**：核心区只放高杠杆信息
2. **缓存命中率**：共享内容形成稳定前缀

**关键设计——顺序即策略**：共享块（世界观/角色文档/角色清单/能力文档）排在任务特定内容（任务标题）**之前**——同角色任务间前缀稳定→缓存命中（实测 cacheRead 82.6%）；任务特定内容沉在稳定前缀尾部。

**冲突与权衡**：
- 动态工具面（pick_tools）改工具列表→前缀变→缓存失效——**专注度与缓存的对抗**——v3 实验结论：模型自然不用时收益大于缓存损失（观察中）
- eager 注入（全文入前缀——缓存友好但 tokens↑）vs lazy 指针（省 tokens 但多一次查询）——按"内容稳定性×复用频率"选：高频稳定 eager、低频变动 lazy

#### 0.8.3 编排原则 → PTH 落点

| 原则 | PTH 机制 |
|---|---|
| 核心区只放高杠杆信息 | system prompt 编排顺序：世界观→角色文档→角色清单→能力文档→任务标题 |
| 工具面裁剪 = 专注 + tokens 双赢 | 工具白名单（三重交集）· pick_tools 动态裁剪 |
| 同样 tokens 更高密度 | description 场景语义化（三要素模板） |
| 开头精炼 | 渐进降输入（任务文本只写核心意图） |
| 高注意力位置注入关键引导 | 负结果 N=3 引导注入会话**结尾**（最新工具结果旁） |
| 低注意力区压缩损失最小 | context-compaction 压中间历史（位置效应直接应用） |
| 稳定前缀优先 | eager/lazy 渲染分层（高频稳定 eager / 低频 lazy） |

### 0.9 记忆理论：锚点-原文统一模型

> 第四个理论根基（2026-08-13 用户）——回答"信息怎么存储与供给才最省专注"。
> 与 0.8 的接口：锚点解决"核心区寸土寸金"与"知识完整性"的矛盾。

#### 0.9.1 统一模型：记忆 = 锚点 + 原文

**任何信息都可以拆成两级**：

| 级 | 定义 | 特征 |
|---|---|---|
| **锚点（anchor）** | "这是什么 / 何时该读原文"的描述 | 轻量（几十 tokens）——可入核心区 |
| **原文（original）** | 完整内容 | 重量（几千 tokens）——外置存储，按需拉取 |

**核心命题**：只要锚点把"什么时候该读原文"描述清楚——原始信息就不必展示给 LLM——只提供锚点，需要时展开。

**工具同理**：概括一套工具的整体作用（族锚点）→ 不加载原始工具列表 → 需要时逐级展开。

#### 0.9.2 锚点质量标准（"描述清楚何时读" = 三要素）

锚点质量决定模型能否**自行判断**"我现在需要它"——锚点三要素：

1. **触发条件**（场景锚点）——什么情况下该读
2. **内容预告**——读原文能获得什么
3. **成本预告**——读的成本（一次查询/展开）

→ 这正是工具 description 三要素模板（是什么/何时用/效果预告）的理论根源。

#### 0.9.3 逐级展开与层级深度权衡

- 两级展开：锚点 → 原文（memory.query 读 role-doc/洞察）
- 多级展开：工具族锚点 → 成员工具 → 参数（空间树层级）

**层级深度权衡**：每级消耗一次查询/决策——层数太多→查询成本吞掉收益——与 0.1 的协调成本边界同构（**锚点层级也是分摊粒度问题**）。

#### 0.9.4 与 0.8 的接口：锚点入核心区，原文入消息流

- 锚点稳定 → 前缀缓存友好；原文变动不影响前缀（查询结果落在消息流中部——低注意力区——损失小）

### 0.10 空间导航理论（综合）

> 第五个理论根基（2026-08-13 用户）——前四节的综合，PTH 的总架构隐喻。

#### 0.10.1 双空间与索引基础

**动作空间**（所有能做的动作）+ **记忆空间**（所有记忆）——两者有良好的索引基础（0.9 锚点体系：asp.index / memory.index / capability-index / worker-index）——LLM 就能在双空间中**自由导航**。

#### 0.10.2 三个导航机制

1. **逐级展开结构**——空间是层级树：顶层概要 → 层级深入 → 具体条目（0.9 逐级展开）
2. **上下文-空间绑定**——LLM 在某空间时，上下文只装该空间内容（工具面 = 该空间动作；知识 = 该空间记忆）——**专注内容按空间分割**（0.8 核心区编排 + 0.1 专注度）
3. **返回简报**——返回上层时带简报（工作总结/洞察）——不是全文带回——空间切换 = 上下文重置

#### 0.10.3 推论：worker 类型分解成为自然行为

设置任务的**硬性分解规范**（子任务→不同 worker→不同空间）：
- **可控**——每步执行有明确边界
- **可见**——任务状态可查（状态机/scorecard）
- **易监督**——产物与简报明确（审批面依赖可判读的输出）

→ 0.1 的"思考量分摊"在空间导航下不是抽象分工，而是**具象的"每个 worker 在它的空间里导航"**。

> **2026-08-14 修订（空间从「先验基板」到「派生结构」）**：上句的旧表述（空间先于 worker 存在）已被替代——
> 每个 worker 的空间**随它分化生成**（新 worker 类型 → 生成其绑定空间），或随注意力管理需要生成（上下文超限 → 生成子空间重置注意力）；
> worker 在**自己的空间里**导航。语言执行基板（ts/python/bash/dev/write）是先验共享的基础设施，不随 worker 生成。

#### 0.10.4 注意力稀释问题的解决

**主会话上下文单调递增**——注意力随时间被稀释（单上下文固有缺陷）。

空间导航的解法：**上下文有界化**——
- worker 上下文：任务结束即清零（无状态——新任务新空间）
- 任务内：空间切换重置工具面；注意力管理需要时**生成子空间即重置**（2026-08-14 修订——生成即重置与切换重置并存）
- 主会话：渐进降输入（只留核心意图——细节沉入 PTH 内部空间）

**空间绑定把"无限增长"变成"空间内增长 + 切换/生成重置"——专注度不随时间衰减。**

### 0.11 交互核：动作空间分类与前后端分离

> 第六个理论根基（2026-08-13 用户）——worker 结构的动作空间维度。
> 交互核 = LLM 与计算机之间的交互层——负责执行 LLM 发出的指令并操作计算机。

#### 0.11.1 统一概念：生产核 + 探索核 → 交互核

之前的"生产核/探索核"是**使用场景**的区别（正式执行 vs 探索验证）——不是核的种类——**同一交互核既可用于生产也可用于探索**——统一为一个概念。

**PTC 范式**：ts 程序组合能力函数——一次执行完成多步逻辑——把多步逻辑从 LLM 轮次卸载到计算机（0.1 思考量分摊的极致：思考归模型，执行归计算机）。

#### 0.11.2 动作空间三分类（嵌套包含——不是并列）

```
③ 纯工具调用（基础工具支撑）⊂ ① 单语言核 ⊂ ② 多语言核
```

| 类型 | 定义 | 适用 |
|---|---|---|
| ③ 纯工具调用 | 无多步逻辑——tool call 序列（能力函数工具化——asp 工具族形态） | 只读规划/快速侦察——不需要写程序 |
| ① 单语言核 | 基础工具 + 一种语言组织方式（纯 ts PTC） | developer——专注单一执行模式 |
| ② 多语言核 | 多个单语言核的结合——**每种语言带职责定位** | origin/executor——全能 + A/B 验证 |

**多语言的"不完全包含"**：多语言 ≠ 语言简单并集——每种语言在 worker 里有职责定位（如 python 负责计算、bash 负责沙盒环境管理）——同时提供多种语言**组织方式**，各自服务不同交互意图。

**嵌套继承**：声明 python 核的 worker 自动获得基础工具面 + python 组织方式——无需重复声明。

#### 0.11.3 与 0.2 高低智力分层的咬合

| 交互核 × 推理档 × 模型 | 角色族 |
|---|---|
| ③ 纯工具 × low × flash | scout/spider——最轻量（不写程序=最低心智负担） |
| ③ 纯工具 × high × pro | planner（写计划靠工具——不写代码） |
| ① 单核 ts × medium × flash/pro | developer——专注单一执行模式 |
| ② 多核 × high × pro | origin/executor/controller——A/B 验证与全栈能力 |

#### 0.11.4 前后端分离（PTH 内部交互核的技术边界，与 PTL/PTH 产品关系无关）

**前端抽象**：模型按一个抽象交互核理解自己的交互对象——WorkerKernel 接口——类型①②③是前端授权面（决定 worker 被授权哪些交互通道）。

**后端实体**：两层——PTH 容器内 ts 核（WorkerKernel 进程内 vm，不经 sandbox）+ sandbox 容器 kernel-host（python/bash 持久 kernel 宿主池，PTH 经 `sandbox-kernel.ts` 客户端持 opaque lease 调用）。`PTH_PYTHON_MODE/PTH_BASH_MODE=kernel` 仅本地调试，切回 PTH 容器内 `PyKernel`/`BashKernel`。

**状态隔离（多租户）**：exec-channel 双模式——stateless（每调用独立 kernel——vm context 新建）/ repl（sessionId 持久 context——变量/函数/声明保留 + idle TTL 回收）——每个 worker 的函数/变量互不泄漏。

**好处**：前端抽象稳定（worker 不感知后端拓扑——加核/换后端无感）· 后端池化（资源效率）· 隔离是安全边界。

#### 0.11.5 实现映射

| 理论元素 | 落点 |
|---|---|
| 交互核声明 | exploreKernels 字段（语义升级：探索核→交互核——含生产+探索） |
| 后端宿主 | `packages/pth-sandbox/src/kernel-host.ts`（`PTH_SANDBOX_KERNEL_URL` + opaque lease；共享密钥仅控制器间认证） |

### 0.12 缓存机制（数据缓存——与 token 缓存区分）

> 第七个理论根基（2026-08-13 用户）——机械化处理大量数据的信息载体。

#### 0.12.1 两个缓存概念（严格区分）

| | token 缓存（prompt cache） | 数据缓存（cache 夹） |
|---|---|---|
| 是什么 | 请求前缀命中——省输入 token 成本 | 模型主动把信息读入的存储夹 |
| 场景 | 每轮 LLM 请求自动发生 | 机械化处理大量数据（读入→多步处理） |
| 指标 | cacheHitRate（cacheRead/(cacheRead+非缓存输入)——已实现） | cacheUtilization（读入后是否使用——✅ 2026-08-13 N3） |
| 理论坐标 | 0.8.2 | 本节 |

#### 0.12.2 数据缓存机制

AI 要机械化处理大量数据 → 读入缓存夹（load）→ 后续步骤反复取用（get）——**避免每步重复读取**（重复读取 = 重复 token + 重复注意力——0.1 专注度）。

**缓存利用率**：读入后是否使用读入数据——set/load → get 配对追踪（按 key + 字符量加权）——读入未用 = 浪费（读入成本已付）。

#### 0.12.3 现有实现与缺口

| 元素 | 落点 |
|---|---|
| 缓存夹本体 | cache-store.ts（随身缓存——元空间级状态——随 asp.cd 携带——与空间本地状态严格区分） |
| 容量约束 | 双上限（字符+条目）——load 超容拒绝 + cache.cancel 腾位——**背包约束**：迫使对信息价值做判断，防无限囤积 |
| 生命周期 | 任务级（任务结束随会话消亡——持久化走 memory.save） |
| ✅ 已补（2026-08-13 N3） | 使用追踪落地——get 命中标记 used → utilization()（字符量加权）→ scorecard.cacheUtilization + 聚合快照 |

#### 0.12.4 设计含义

1. cache-store 加使用追踪（key 级 loaded→used 配对）
2. scorecard 新增 cacheUtilization（与 cacheHitRate 命名严格区分）
3. sensor 观测新维度：**数据流效率**——低利用率=读入未用浪费信号——引导/JIT 优化缓存策略（0.7）

> **（2026-08-13 N3 已落地）**：使用追踪 utilization() → scorecard.cacheUtilization + 聚合快照（sumCacheLoaded/sumCacheUsed）→ sensor:worker-opt 观测维度 + cache-waste 热点（窗口 ≥3 任务、载入 ≥500 字符、利用率 <50%）——§10 N3 勾销。

### 0.13 生态转化（外部生态接入流程）

> 第八个理论根基（2026-08-13 用户）——主流 agent 扩展生态的统一接入。

#### 0.13.1 按类型分流映射

```
主流生态：skill / plugin / pi-extension / MCP
        │
        ├─ 知识型（skill）──▶ 记忆区（0.9 锚点-原文条目化）
        │
        └─ 工具型（plugin/pi-extension/MCP）──▶ 交互核扩展（0.10 前端授权面）
                                                └─ 源码拆解重实现（不是转接器）
```

**工具型生态（MCP/extension/plugin）——不写转接器，拆解源码实现**：

| 方式 | 问题 |
|---|---|
| ❌ 转接器（运行时桥接） | 依赖外部运行时/协议——黑盒不可审查/修改——无原生治理（权限/隔离/门控进不去） |
| ✅ 源码拆解重实现 | 拿到生态工具源码→分析其实现→用 PTH 交互核语言重写——变成 PTH 原生能力函数——彻底无外部依赖 |

**源码拆解的收益**：
- 工具进入 PTH 原生治理（capabilities 白名单 / 状态隔离 / EXEC_TOOL_CAP）
- 可审查可修改（安全边界——审计可覆盖）
- 与描述三要素/缓存/scorecard 全链路兼容
- 无协议开销、无外部进程依赖

**"使用那种语言看适配程度"——重实现语言选择**：拆解后按原源码与 PTH 核的适配度选重实现语言（TS 生态→ts 核重写；Python 生态→python 核重写；MCP→拆 server 源码提取工具逻辑→按逻辑归属选核）。

**已验证先例**：agent-reach 扩展——拆解 OpenCLI/各平台 API 调用逻辑，用 ts 重写为 toolstore 扩展（非运行时加载 OpenCLI）。

#### 0.13.2 转化流程三步

1. **分类**——知识型（skill：指令/流程知识）vs 工具型（plugin/extension/MCP：可调用能力）
2. **转化**——知识型：SKILL.md → memory 条目（锚点+原文——role-doc 式）；工具型：**拆解源码→用交互核语言重实现**（工具 + **场景化描述三要素**——0.9.2 锚点标准——否则工具不可用）
3. **门控**——capabilities 白名单 + EXEC_TOOL_CAP（安全边界）

| 生态 | 落点 | 状态 |
|---|---|---|
| plugin/pi-extension（TS） | toolstore/extensions（ext-registry——agent-reach 已验证） | ✅ 已有 |
| skill | 记忆区条目化 pipeline（SKILL.md → memory 条目） | ⚠️ 无转化流程 |

### 0.14 猜想：伪世界模型〔猜想〕（2026-08-14 用户）

> 猜想陈述：综合足够多的开放数据源，以及足够的机械化分析工具，能否构造一个系统，使其对**整个世界**有充分而深刻的认识？——「深刻」= 能在**一定尺度**上预测世界的整体演变规律。

#### 0.14.1 「伪」在哪里：不是训练，是组装

- **神经世界模型**（对照片）：用参数学习环境动力学——黑盒、难审计、训练代价≈世界复杂度；
- **伪世界模型**：开放数据源 + 机械化分析工具 + LLM 调度层，**组装**出一个功能上像世界模型的系统——白盒（每个结论都有数据与工具来源）、可增量（新数据源/新工具即插即用）、代价远小于世界本身；
- 与 0.3 智力代偿同构：机械化分析工具代偿「理解世界」的智力负担——代偿对象从单任务放大到世界尺度。

#### 0.14.2 尺度分层：猜想在哪里成立（2026-08-14 分析——待用户复核）

| 层 | 例 | 可预测性 | 依据 |
|---|---|---|---|
| 机械层 | 天体轨道 · 化学 · 工程 · 短期天气 | 可预测〔可行〕 | 定律稳定 + 确定性计算 |
| 统计层 | 人口 · 流行病 · 粗粒度经济 | 概率可预测〔可行〕 | 大数定律 + 置信区间 |
| 涌现层 | 政治 · 时尚 · 技术突破 · 短期市场 | 不可预测〔边界〕 | 混沌 · 涌现 · 反思性 |

**裁定**：猜想在机械层与统计层成立、在涌现层不成立——伪世界模型的天花板**不是数据量，是世界的可分性**（与 0.4 边界条件 2 同构：可预测的下沉，不可预测的标记）。

#### 0.14.3 四堵墙（不可逾越的边界）

1. **混沌**：微观不确定性指数放大——即使确定性系统也有预测地平线（天气 ~10 天）；
2. **涌现**：整体 ≠ 部分之和——社会/市场的规律产生于交互，机械分析各组成部分拼不出交互产生的结构；
3. **反思性**：预测改变被预测对象——伪世界模型越被使用，越改变它所建模的世界（自我实现/自我否定）；
4. **自指**：被建模的世界包含模型自身——自身的数据、算力、预测行为都是世界的一部分，全知要求模拟自己（无穷回归）。

#### 0.14.4 深刻的重定义：不是全知，是校准

- 「深刻」不可定义为全知预测——四堵墙内不存在；
- **可操作定义：可预测性地图（predictability map）**——对每个尺度回答三问：什么可预测 / 预测地平线多长 / 置信度多少；外加**相变预警**：检测可预测层何时滑向不可预测层；
- 伪世界模型的产品不是预测本身，是「知道自己知道什么、不知道什么」——0.4 边界条件的机器实现。

#### 0.14.5 与既有理论的咬合（终局形态）

- 命题 2（记忆量分摊）的终局：世界模型 = 终极外置记忆——wiki 百科（90 条）是种子，数据源接入是扩土；
- 0.3 智力代偿的终局：机械化分析工具 = 终极代偿器——bash/python/SQL 核已是分析工具原语（属串联代偿〔已立〕范畴）；
- 0.7 优化理论的终局：JIT 环让伪世界模型自我改进——错误预测 → 修正规则 → 复测；
- 0.4 可分性条件的直接应用：可预测的下沉、不可预测的标记——四堵墙是边界条件的特例。

#### 0.14.6 PTH 落点（已有 vs 待建）

### 0.15 agent 行为分析一般方法（2026-08-14 用户）

> 方法陈述：要想优化一个 LLM 的推理，就需要理解它在任务中**发现了哪些信息**、**基于这些信息做了什么**——从而还原出原始思考路径，找出**岔路口**，以及**记忆/工具缺了哪些**。

#### 0.15.1 两个数据维度：信息发现 × 行为

- **信息发现（输入侧）**：『它知道什么』——每步工具结果/记忆查询返回/能力索引/源码阅读——按时间序记录**新发现的信息**（第一次见到，不是重复读）；
- **行为（输出侧）**：『它决定做什么』——基于已知信息发出的动作（调了哪个工具/查了什么/写了什么）；
- 二者对位 = 思考路径的骨架：**信息 X 到达 → 行为 Y**——「知道 X 才做 Y」的因果链。没有信息依据的行为 = 盲试；有信息但没用上的行为 = 冗余。

#### 0.15.2 思考路径还原（三段法）

1. **发现链**：时间序排列「每一步新发现的信息」——还原模型的**信息增量曲线**；
2. **决策链**：每个行为关联其前置信息——基于哪个发现做的这个动作（行为-信息对位）；
3. **意图链**：行为序列语义归纳（探索→验证→实现→提交——五步工作流的实际走法，含岔路与折返）；
- 产物 = **思考路径图**：发现链/决策链/意图链三层对位——所有后续分析的公共底图。

#### 0.15.3 岔路口定位（优化的断点）

- 岔路口 = 信息到达后**存在多个合理分支、模型选了较差分支**的点：
  - **重复探测**：信息已到手仍重查（不知道已有——记忆侧）；
  - **盲试**：信息缺失却不检索、直接猜（工具/记忆缺引导）；
  - **迂回**：选了长路径，而短路径所需信息当时其实可得；
- 定位方法：比较**实际走法** vs **信息完备时的最短走法**——分歧点即岔路口（参数指纹/负结果收敛是其中的机械化特例）。

#### 0.15.4 缺失诊断：记忆缺口 vs 工具缺口

- **记忆缺**：行为显示「该查而没查到的知识」——模型不知道有这条记忆（锚点缺失/不可检索）→ 补锚点/条目；
- **工具缺**：行为显示「想做而做不了的动作」——幻觉工具名/错误工具/降级绕行 → 补工具/别名/能力索引；
- 判别线：失败点落在**检索侧（记忆）**还是**执行侧（工具）**。

#### 0.15.5 与既有理论的咬合

- 0.7 优化理论的**前置方法**：JIT 内环 collect 阶段的具体做法（观测端升级）；
- 命题 3（专注度）的**诊断工具**：噪音 = 「发现了但没用的信息」；
- 0.9 锚点-原文的**质检工具**：查不到的锚点 = 无效锚点；
- 0.14 可预测性地图的**行为侧原型**：路径还原 = 给单任务建微观地图。

#### 0.15.6 PTH 落点（现有机制即分析器）

| 分析构件 | PTH 落点 | 状态 |
|---|---|---|
| 发现链/决策链原始数据 | trace 事件流（llm-call/tool-call/tool-result）· transcript | ✅ 已有 |
| 意图链 | CoT 压缩（行为过程/思维过程/坑与修正）= 模型自述 | ✅ 已有 |
| 岔路口机械化检测 | 参数指纹 · 负结果收敛 · unknown-tool 引导（N12 护栏） | ✅ 已有 |

### 0.16 任务拓扑与穿透（递归 agent 的等效替代——2026-08-14 用户）

> 依据：Prime Agent rlm() 官方文档（rlm.md——2026-08-14 调研）+ 面板裁决「持久性的单位是任务，不是会话」。
> 三个子概念：类型树（谱系语义澄清）→ 任务投递 = rlm 等效（入口类型由 PTL 派发逻辑决定）→ 穿透（固化捷径边）。

#### 0.16.1 谱系是类型树，不是实例树

- worker 谱系（Origin → actuator → executor → developer → coder）描述**类型**——每个节点是 worker 类型（角色定义）；
- 实例 = batch 副本（类型 × 副本数，PTH_WORKER_ROLES 配比）——进程生命周期独立（fork/回收/扩缩容）；
- **子 worker 类型 = rlm() 持久化 agent 的等效物**：类型持久存在（可寻址、可续派、可恢复），
  **按需添加**（分化提案 → 裁决 → 注册——即 rlm 的 spawn 语义落在类型层，不在会话层）；
  实例按需 spawn/回收——Prime 的「持久子会话」在 PTH 由「持久类型」承载。

**组织权传播（2026-08-14 用户裁决 A）**：
- **逐级继承**：每个类型拥有组织自己子树的能力——父类型对自身子树信息理解充分（谱系蕴含），
  actuator 组织四族、executor 组织 developer/writer、developer 组织 coder/tester、explorer 组织 scout/spider、researcher 组织 analyst/memory-keeper、analyst 组织 prospector/solver、prospector 组织 predictor——递归向下；
- **规划/设计类补充**：planner（组织知识专有——plan/design）与 governor（oversight）获得**跨子树组织补充权**
  （可组织非自己子树的执行类型——如 planner 组织 developer 做方案落地）；
- origin 保持全树组织权（根）；
- 组织权 = 任务投递权的来源（0.16.2）——谁能向哪个类型投递任务，由组织权判定。

**分化轴（2026-08-14 用户裁决——按「负责的问题类型」二分）**：
- researcher 族 analyst 升中间层，按问题类型二分：**开放探索型**（无定解/发散——假设生成/解空间勘探）
  → prospector（勘探者，其下再分 predictor 预测专精）；**封闭限制型**（有约束/收敛——推导/证据验证）→ solver（求解者）。
- **范围（用户裁决 A）**：此轴**只在 researcher 族**落地——executor/explorer 用各自职责轴（实现/测试、侦察/抓取），不套此轴；「开放/封闭」不设为全局正交轴（避免各族长重复子树）。

#### 0.16.2 任务投递 = rlm() 等效（入口类型由 PTL 派发逻辑决定）

- **任务投递即 spawn**：使用高级 worker（父类型）时，对子 worker 类型的调用 = **任务投递**——
  把任务提交给目标子类型执行，即实现 rlm() 的等效效果：子类型 = 持久化 agent（可寻址/可续派/按需添加），
  父 = 投递方；任务拓扑 = **类型树上的派发路径**，不是运行时长出来的 agent 树；
- **入口 worker 类型**：哪个类型充当默认入口（旧稿以 Origin 为例——**仅为示例，非规定**），
  由 **PTL 任务派发逻辑**决定；
- **前置未定项（2026-08-14 用户声明）**：PTL 的任务派发逻辑与交互逻辑**尚未设计**——
  本节的入口语义/派发路径/交互协议待该设计完成后回填（关联 §8.3 W8）；
- **与 Prime 的对照**：Prime 在运行时 spawn 持久子 agent 长成树；PTH 是**静态类型树 + 任务投递**——
  「展开成图，而不是长成树」（图的节点 = 类型，边 = 投递/回流）。

#### 0.16.3 穿透（penetration）

- **定义**：优化循环（0.7 环）发现某条「父类型 → 子类型」派发路径是**稳定高效工作流**时，
  **注册成一种特殊 skill**——此后同类任务由父**直接调用子 agent**，跳过逐级派发与任务池往返，
  减少传播损耗；
- **穿透 = 类型树上的固化捷径边**：普通边 = 任务池往返（提交→路由→认领→执行→回流）；
  穿透边 = 直接调用（父 worker 任务内直呼子类型——子 agent 承接，产物按契约回流）；
- **形态**：穿透 skill = 特殊 skill 类型（区别于普通 SOP skill——§8.3/B4）：
  封装「哪个子类型、输入契约、产物契约、适用场景三要素」；
- **与 0.3.6 的关系**：穿透是**串联代偿的拓扑捷径**——不旁路 LLM（子类型仍是 LLM worker），
  旁路的是传播层级；并联代偿（旁路 LLM 直接接管）仍是独立待议项，两者不可混用；
- **治理**：注册走优化通道 + 审批面（发现 → 提案 → 裁决 → 注册——与 T6 空间生成同构）；
  注册后不可变（skill 治理——§8.3/B4）；
- **与 rlm 的对照**：穿透 skill ≈ **编译后的 rlm 调用点**——把「运行时决定 spawn」固化为
  「稳定调用边」（rlm 是解释执行，穿透是 JIT 编译产物——与 0.7 同构）。

#### 0.16.4 PTH 落点（现状 vs 待建）

|---|---|---|

## 1. 系统定位（v2）

**PTH = 自耦自然语言解释器（解释即执行）。**

输入自然语言意图，直接产出执行结果。内部解释执行机制：

```
任务池 → 角色路由 → worker 执行 → 产物提交 → 应用
                ↑                        ↑
           自我调节（控制论外环）    按需优化（JIT 内环）
```

一句话：**把工作正交分解给专职角色，每个角色在它的空间里以最小工具面闭环完成任务（空间导航），系统用多级闭环持续优化自己——所有自改变经过人工裁决闸门。**

理论→定位：§0.10 空间导航是执行隐喻；§0.7 多级闭环是演化隐喻；两者经"硬性分解规范"衔接。

### 1.1 实现结构（2026-08-13 用户裁决）

```
项目
├─ PTL（基于 pi 的多环境共存平台）：pi 会话 + 扩展（pth-notify 等）——通过 pth-cli 派发/裁决调用 PTH
└─ PTH（自耦自然语言解释器）
    ├─ 数据库（postgres——任务/记忆/trigger 存储 + redis 辅助）
    ├─ sandbox（核宿主池——交互核后端——0.11.4）
    └─ 主容器（pi-platform）
        ├─ trigger——时序/事件中枢（统一触发派发/调参/通知）
        ├─ worker 池——角色循环（peek→claim→run）
        └─ 任务池——排队/claim 认领
```

**极简内核哲学**：主容器内就三件事——任务池（世界状态）、worker 池（执行者）、trigger（时序）——其余一切（优化循环/通知/派生/核后端/参数）下沉到扩展、数据库、sandbox、trigger 规则（后天扩展实现——非必要不添加）。

**硬边界原则**：阈值/窗口/TTL/池参数不硬编码主动提供——只提供调节接口（perf-params）——默认值在配置层。

### 10.1 护栏统一抽象（N12 设计——2026-08-14）

> 背景（2026-08-14 用户审计）：七层护栏已清点，但无统一抽象——三种不一致：阈值三处混放（硬编码常量 / 配置中心 `PTH_AGENT_*` / env 直读）、「计数→引导→终止」三段式手写五遍、处置语义 soft（ok+warning）/hard（ok:false）混用。B1 验证任务被负结果收敛软终止截断正是语义混乱的表现。

**认知模型**：护栏 = 0.14 伪世界模型「相变预警」的微观版——检测系统从「可预测层」滑向「失控层」，在相变点前制动。

**统一形态（三段式）**：
- **观测（signal）**：每步事件（hit/reset）由调用点判定（指纹比对/负结果语义/空 done 判定——信号来源各异，保留在调用点）；
- **判定（verdict）**：守卫实例持有连续计数 + 阈值——阈值全走配置中心（perf-params，`PTH_GUARD_*` 键，运行时可调）；
- **处置（action）**：语义统一——`guide`（回填引导消息继续）/ `soft`（软终止：ok+warning）/ `hard`（硬失败：ok:false）。

**豁免矩阵（声明式）**：`{ guardId → roleId[] | 谓词 }`——T5 侦察豁免（negative-loop：scout/explorer）进矩阵；B1 遗留「治理族（acceptor 等）是否豁免负结果收敛」已裁（2026-08-15 D2 custom）：**不做治理族豁免**，改为负结果收敛阈值 5→15 全局放宽（sensor 留观测窗口；失败任务回收机制缺失期不过早强制闭合）。

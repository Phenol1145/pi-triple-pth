1. 上一轮发现的租户隔离、正式领域知识晋升、能力组合、审核身份和委派领域继承问题没有被修复；

> **K5 评测资产已落地，数据结构自洽；生产知识闭环与质量门槛尚未通过验收。**

不建议继续使用“v1.2 K0–K5 + 评测批全部完成”作为发布状态。

### 2.2 本报告使用的稳定术语

- **Role**：任务中的操作职责，例如 `solver`、`controller:adversarial`、`memory-keeper`；不是学科分类。
- **Domain**：任务涉及的知识范围，例如 `programming-languages`、`materials-science`；同一任务可绑定多个 Domain。
- **KnowledgeContext**：在任务执行前生成的、租户与空间可见性受控、有界且可重放的 official knowledge 快照。
- **Candidate**：任务 outcome 提炼后形成、尚未通过验证的 draft knowledge。
- **EvidenceRef**：从知识声明指向来源、版本和具体定位位置的结构化证据引用。
- **VerificationPlan**：规定候选所需领域审核、对抗审核、审核主体和候选版本的验证计划。
- **Official Knowledge**：通过完整门禁、可审计、可重放并可供正常检索使用的知识。

### 2.3 判定原则

本报告区分以下三种状态：

1. **工程检查通过**：代码可构建，现有测试无失败；
2. **组件能力存在**：相应接口、数据或纯函数已经实现；
3. **组合验收通过**：真实生产路径满足隔离、授权、证据、并发、重放和质量指标。

只有第 3 项可以支持阶段 `done`。测试通过不能替代缺失的验收场景。

## 5. 验收阻塞项

### AB-01：Memory 的租户身份不是复合身份

**严重度：Critical**

`memory_entries` 仍使用全局 `id` 主键：

- `packages/pth-memory/src/schema.ts:6-8`
- `packages/pth-memory/src/memory-store-pg.ts:104-107`
- `packages/pth-memory/src/memory-store-pg.ts:157-175`

写入会仅按 `id` 锁行，并执行 `ON CONFLICT (id) DO UPDATE`。tenant B 使用 tenant A 已存在的相同 ID 时，会更新 A 的记录，且原 tenant_id 不变。

此外：

- memory bridge 虽读取认证 tenant，却未把它传入 Facade 的 query/retrieve/get；
- Broker 的 retrieve/search/get 使用 grant tenant，但 raw `query` 通道没有 tenant/status 约束；
- sandbox 静态 bridge token 通道仍绕开每次执行的 grant 语义。

**影响**：跨租户数据完整性破坏和潜在越权读取。

**关闭条件**：

1. 通过有序 migration 建立至少 `(tenant_id, id)` 复合唯一身份；
2. 所有 repository 操作强制接收 `TenantScope`，不允许隐式 `default`；
3. bridge 与 Broker raw query 在数据层强制 tenant/status/space predicate；
4. 增加同 ID 跨租户写入、读取和并发负向测试。

### AB-02：Official domain knowledge 的 provenance 布局不一致

**严重度：Critical**

系统契约、Refiner 和 `canPromote` 使用 `meta.provenance`：

- `packages/pth-memory/src/knowledge-provenance.ts:6`
- `src/pth/kernel/execution/refiner.ts:259-266`
- `src/pth/execution/knowledge-verdicts.ts:75-78`

但 `PgMemoryStore.write` 对 official `domain-fact/domain-method` 校验整个 `entry.meta` 根对象：

- `packages/pth-memory/src/memory-store-pg.ts:91-97`

合法 draft 获得双 pass 后，真实 promotion 最终会抛出 `provenance.sourceTaskId is required`。

K5 seed 在 `scripts/seed-k5-pilot.ts:55-66` 同时平铺和嵌套 provenance，只是数据导入 workaround；正常 candidate promotion 仍然失败。

**关闭条件**：建立唯一 canonical metadata schema，并用真实 PostgreSQL 跑通 `domain-fact` 与 `domain-method` 的 draft → verdicts → official 链路。

### AB-03：KnowledgeContext 覆盖治理能力

**严重度：Critical**

角色装配为 adversarial 和 memory-keeper 提供：

- `knowledge.review`
- `knowledge.promote`

位置：`src/pth/impls/kernels/capability.ts:222-245`。

AgentTaskRunner 随后注入完整 `knowledge = { context }`：

- `src/pth/runner/agent-task-runner.ts:127-139`
- `src/pth/kernel/ptc/runner.ts:55-61`
- `src/pth/impls/kernels/ts-interpreter.ts:52-55`

解释器按顶层键直接赋值，因此 production task 启用 KnowledgeContext 后，`review/promote` 消失，即使 context 为空。

**关闭条件**：对嵌套 capability 做明确组合，或将只读上下文与治理动作拆成不同 capability root；增加真实组合测试。

### AB-04：Verifier 与 Promoter 身份仅为字符串标签

**严重度：Critical**

`KnowledgeVerdict` 没有以下字段：

- candidate revision；
- domain ID；
- verifier principal；
- verifier execution/task ID；
- verification evidence。

HTTP `/knowledge/verify` 没有角色权限检查；普通认证调用者提交 adversarial verdict 时会被硬编码为 `controller:adversarial`。`/knowledge/promote` 同样不验证调用主体是否为 memory-keeper，也不传递 tenant。

位置：

- `src/pth/execution/knowledge-verdicts.ts:10-20`
- `src/pth/gateway/routes-kernel.ts:289-320`
- `src/pth/application/gateway/pth-gateway-facade.ts:197-202`

**影响**：一个 tenant-agent 可以模拟 domain reviewer、adversarial reviewer 和 promoter，逻辑上的“三方分离”不构成安全边界。

**关闭条件**：引入持久化 `VerificationPlan`，把 required domains、candidate revision、principal、execution、grant 和 verdict evidence 绑定，并在路由和 service 两层授权。

### AB-05：Delegate 丢失父任务 Domain envelope

**严重度：High**

`TaskDispatchContext` 与 `TaskDelegateInput` 不包含 `domains/domainBinding`，TaskLoop 盖章和 `TaskControlService.delegate` 构造子 payload 时也不传递；store 对 delegate 又不会重新执行 resolver。

位置：

- `src/pth/contracts/tasking.ts:91-122`
- `src/pth/bootstrap/task-loop.ts:45-60`
- `src/pth/tasking/task-control-service.ts:140-166`
- `src/pth/kernel/storage/task-store-pg.ts:149-170`

结果是任意父任务通过 `tasks.delegate` 生成的子任务都会得到 `domains=[]`，后续 KnowledgeContext 无法检索领域知识。

**关闭条件**：将经服务器验证的 Domain envelope 纳入 dispatch context；默认完整继承，只允许显式、可验证的子集收窄。

### AB-06：K5 live 评测没有运行生产 Resolver

**严重度：High**

offline 与 live 都使用 `buildPilotCatalog()`：

- `scripts/eval-k5-pilot.ts:57-72`
- `src/pth/catalog/data/pilot-domain-overrides.ts:19-89`

该 Catalog 注入专供评测的 aliases。生产 Host 与 batch process 只从原始 `DISCIPLINE_DEFINITIONS` 构建 Catalog：

- `src/pth/kernel/assembly.ts:157-161`
- `src/pth/bootstrap/batch-process.ts:76-85`

同一 60 题的实测结果：

| Catalog | domainRecall@3 | knowledgeRecall@5 | 失败数 |
|---|---:|---:|---:|
| K5 evaluator-only Catalog | 1.0000 | 1.0000 | 0/60 |
| Production Catalog | 0.0000 | 0.0000 | 60/60 |

更严重的是，两份行为不同的 Catalog 都报告版本 `d8429659`，因为 Catalog hash 没有覆盖 aliases、描述和各类 anchors。

**结论**：当前报告的 “live” 仅表示知识行来自 PostgreSQL，不表示生产 Resolver、Broker、ContextProvider 或 capability 路径被测量。

### AB-07：knowledgeRecall@5 是固定 top-5 的自证循环

**严重度：High**

`rankKnowledgeForDomains` 只接收 domains，按 Domain/祖先 anchor 数与 ID 排序，不读取：

- query text；
- knowledge content；
- evidence quality；
- source authority；
- freshness 或 valid-time。

位置：`src/pth/catalog/pilot-evaluator.ts:50-72`。

`pilot-knowledge.ts` 又明确给每域五条 core knowledge 添加完整祖先链，使它们固定进入 top-5。60 条查询的 expected IDs 恰好只覆盖这两个固定 top-5；其余 14 条 seeded knowledge 没有被 recall 指标检验。

只要问题还能解析到 Domain，问题语义或 knowledge content 是否相关都不影响 `knowledgeRecall@5`。

**关闭条件**：评测器必须调用生产检索接口并采用 query-sensitive ranking；加入 hard negatives、混淆领域、零结果、无关内容和顺序扰动测试。

### AB-08：evidenceCoverage 在无证据时仍可满分

**严重度：High**

当前逻辑为：

```ts
top5.every((entry) =>
  entry.evidence.every((evidence) => sourceIds.has(evidence.sourceId)),
)
```

当 top-5 为空或 `entry.evidence=[]` 时，`every()` 的真空真值会返回 `true`。实测空 evidence 仍得到 `evidenceCoverage=1` 且查询 pass。

位置：`src/pth/catalog/pilot-evaluator.ts:109-120`。

live 模式也不是从数据库读取 evidence，而是按 row ID 从离线 `PILOT_KNOWLEDGE` 回填：

- `scripts/eval-k5-pilot.ts:71-92`

因此数据库缺少 evidence、source rows 或 structured locator 时，live coverage 仍可能满分。

**关闭条件**：

1. authoritative query 必须至少命中一条 expected knowledge；
2. 每条被计入的 knowledge 必须至少有一条非空 EvidenceRef；
3. EvidenceRef 必须从数据库读取，并关联实际 source registry row；
4. source/version/locator/license/hash 门槛必须 fail-closed。

## 6. 其他高优先级缺口

### 6.1 Candidate 生成不可恢复

`BoundedBackgroundQueue` 为进程内队列，达到容量会丢弃任务；TaskLoop 为每个任务创建队列并 fire-and-forget 提交 Refiner。

- `src/pth/tasking/task-outcome-observers.ts:37-55`
- `src/pth/bootstrap/task-loop.ts:125-143`

进程退出、队列压力或异步失败都可能使 committed outcome 永久不产生 Candidate。需要以 task/lease generation 为幂等键的事务 outbox。

### 6.2 Candidate 缺少领域与结构化证据

RefineInput 没有完整消费 `work.domains` 和最终 outcome；无 artifact 时来源退化为 `task:<id>`。Candidate 无法表达：

- required domains；
- primary/auxiliary domain；
- outcome/artifact lineage；
- structured EvidenceRef；
- source/version/valid-time。

这使后续 VerificationPlan 无法决定需要哪些领域审核。

### 6.3 Promotion 缺少 CAS、事务和幂等语义

当前 promotion 是 `get → canPromote → write`，没有：

- candidate revision CAS；
- verdict 与 promotion 的事务串联；
- canonical ID / dedupe / supersedes；
- idempotent replay；
- index refresh event。

`PgMemoryStore.update` 也不会生成 revision，reject/verdict 的完整历史不可靠。

### 6.4 Source registry 不是内容快照

`PilotKnowledgeSource.contentHash` 实际为：

```text
sha256(uri | version | authority)
```

位置：`src/pth/catalog/data/pilot-source-registry.ts:21-26`。

它是 registry metadata fingerprint，不是来源内容 hash，无法证明：

- source content 未漂移；
- locator 仍指向相同段落；
- 某个旧版本可以重放；
- license 在该版本下有效。

建议将其重命名为 `registryFingerprint`，并另外保存不可变 source artifact 或其真实 `artifactHash`。

### 6.5 Structured EvidenceRef 在 seed 时丢失

`PILOT_KNOWLEDGE` 中 evidence 为 `{sourceId, locator}`，但 seed 时只把 locator 字符串写入 `provenance.sourceRefs`：

- `scripts/seed-k5-pilot.ts:55-66`

数据库记录没有结构化 sourceId、retrievedAt、license 或 source revision。live evaluator 的离线回填掩盖了这一缺口。

### 6.6 当前 60 题不是完整 Phase 5 题型

当前题集主要是每域五个 core 主题的同义改写，尚未覆盖：

- 多 Domain 组合；
- 相近 Domain 混淆；
- 来源冲突；
- 跨版本答案变化；
- 缺失知识与拒答；
- evidence locator 漂移；
- tenant/space 可见性差异。

同一 commit 同时定义 aliases、knowledge、queries 和 expected IDs，缺少独立 holdout 或盲评流程。

### 6.7 Audit observer 在真实组合测试中失败

完整测试运行期间，真实 batch process 多次输出：

```text
observer failed: Cannot read properties of undefined (reading 'pool')
```

TaskLoop 把 `audit.write` 方法从对象上解引用后再调用：

- `src/pth/bootstrap/task-loop.ts:126-128`

而 `PgAuditStore.write` 依赖实例的 `this.pool`：

- `src/pth/kernel/storage/audit-store.ts:17-24`

这会丢失 `this` 绑定，使 committed task 的 audit observer 失败；observer 容错机制仅记录警告，因此完整测试仍为绿色。

**影响**：任务可以 completed，但对应 PG audit event 缺失，削弱 promotion 与任务闭环的可追溯性。

## 7. K5 评测可信度结论

### 7.1 当前指标可以证明什么

当前 `1.0/1.0/1.0` 可以证明：

- 评测专用 aliases 能解析当前问题；
- 当前 expected IDs 存在于固定 top-5；
- 离线 knowledge 的 sourceId 能在离线 registry 中找到；
- 相同进程内输入会得到确定性输出。

### 7.2 当前指标不能证明什么

它不能证明：

- 生产 Resolver 能正确识别这 60 个问题；
- KnowledgeBroker/KnowledgeContext 能检索语义相关知识；
- 数据库记录包含完整 evidence；
- tenant、space 和 official status 在评测中生效；
- source content 可按版本重放；
- Candidate 经真实双审核与 promotion 后可被检索；
- 跨 Domain、冲突来源和无答案场景表现达标。

因此，[K5 冻结评测报告](./k5-eval-report.md) 的数值应标注为 **fixture self-consistency baseline**，不能作为 production acceptance metric。

| 带 Domain 的父任务执行 delegate | 子 payload 无 `domains/domainBinding` |
| Broker raw query 使用 tenant-a grant | 可返回 tenant-b row |

### 8.3 测试解释

完整测试绿色是有效工程证据，但当前测试未覆盖：

- 相同 memory ID 的跨租户写入；
- production Catalog 跑 K5 冻结题；
- 空 top-5 / 空 evidence；
- K3 context 与 K4 governance capability 的组合；
- 真实 `domain-fact` promotion；
- root publish → delegate → claim → KnowledgeContext；
- process restart 后 Candidate outbox replay；
- 真实 verifier principal/execution separation。

## 9. 建议修复路线

### Gate A：发布阻塞修复

1. 建立 `(tenant_id, id)` identity migration，并强制 TenantScope；
2. 统一 canonical knowledge metadata 与 provenance 布局；
3. 修复 Knowledge capability 的嵌套组合；
4. 为 verify/promote 建立真实 RBAC、grant 和 principal/execution 绑定；
5. 让 delegate 继承并验证 Domain envelope；
6. 修复 audit observer 的方法绑定并断言 audit row 落库。

**退出条件**：上述每项均有真实 PostgreSQL 或生产组合回归测试，且对应负向场景 fail-closed。

### Gate B：可信知识闭环

1. 引入事务 outbox 与确定性 Candidate idempotency key；
2. Candidate 持久化 domains、outcome、artifacts、EvidenceRefs 和 lineage；
3. 建立 VerificationPlan 与每 Domain 独立 verdict；
4. Promotion 使用 candidate revision CAS、事务、幂等重放和完整 revision；
5. 建立 source snapshot、artifactHash、valid-time 与 license policy。

**退出条件**：`claim → context → outcome commit → outbox → candidate → per-domain/adversarial verification → promotion → broker retrieve` 在进程重启与并发条件下可重复通过。

### Gate C：重建 K5 质量评测

1. evaluator 直接调用生产 Catalog、KnowledgeBroker 与 KnowledgeContextProvider；
2. 结果记录 catalog/corpus/source/row versions 和选中 entry IDs；
3. ranking 引入 query relevance，并保留稳定 tie-break；
4. evidence 必须来自数据库且非空，关联 source/version/locator；
5. 加入 hard negatives、无答案、混淆 Domain、跨 Domain、冲突来源和跨版本题；
6. 将题集与 aliases/knowledge 的制作流程分离，增加 holdout 和独立复核；
7. 在 CI 中同时运行离线 snapshot 与真实 PostgreSQL/生产路径评测。

**退出条件**：生产路径而非评测专用路径达到既定阈值，并且反事实测试能够使指标下降。

### Gate D：按证据扩展

只有 Gate A–C 全部通过后，才扩展更多领域、向量/混合检索、`asOf` 查询、知识冲突图、supersedes 关系和 JIT specialist Role。

## 10. 最终结论

当前版本相较 `75ba9ea` 有明确进展：K5 不再只有设计文档，而是具备可执行数据、脚本与测试。但是，这一进展尚未改变总体验收状态。

最终判定为：

> **工程基线通过；K5 评测资产通过；K5 生产质量、K1–K4 组合闭环与 v1.2 总验收不通过。**

建议立即把任务账本中的“全部完成”调整为“评测资产完成 / production acceptance blocked”，并以 Gate A → Gate B → Gate C 的顺序闭合，而不是继续扩展新的知识领域。

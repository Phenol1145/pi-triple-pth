## 3. 发布阻塞问题

### P0-1：revision/version 不变量被破坏

`PgMemoryStore.write` 判断 status/meta-only 变化为非幂等并写入旧 revision：
[memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L142-L176)。但 UPSERT 的
version 分支只比较 content 与声明的 `meta.version`：
[memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L192-L203)。

真实 PostgreSQL 探针使用唯一租户并在结束时清理，结果为：

```json
{"v1":1,"v2":1,"secondError":"23505","revisions":[1]}
```

即第一次 status/meta-only mutation 写入 revision=1 后，当前 version 仍为 1；第二次 mutation
再次插 revision=1，触发唯一约束 `23505`。这会直接破坏 promotion 后继续审核、修订或归档。

同时，promotion 仍是 `get → canPromote → write`：
[knowledge-promotion.ts](../../src/pth/execution/knowledge-promotion.ts#L93-L130)，没有把
candidate revision 检查、verdict 消费、official 写入和索引事件放入同一事务。

**关闭条件：**统一 write/update 的变更判据和 version 递增规则；为 promotion 提供
`tenant + candidateId + expectedRevision + status=draft` CAS，并在同一事务写入不可变决定、
official 状态、revision 与后续 outbox。

### P0-2：raw SQL 只有入口授权，没有数据面租户隔离

Gateway 已限制 tenant-agent 调用 raw query，但 facade 明确忽略 tenant：
[pth-gateway-facade.ts](../../src/pth/application/gateway/pth-gateway-facade.ts#L83-L85)。Broker
也直接执行 caller SQL，只做事后 space 过滤：
[knowledge-broker.ts](../../src/pth/execution/knowledge-broker.ts#L112-L142)。

这没有满足原报告要求的 tenant/status/space 数据层谓词。`platform-admin` 是谁可以调用的
授权问题，不是返回哪些租户数据的隔离证明。

**关闭条件：**raw query 必须走受限查询 AST/视图/行级策略之一，由服务端强制 tenant、status
和 space 条件；增加跨租户真实 PG 负向测试。若决定 platform-admin 可跨租户，必须另行裁决
并要求显式目标租户与审计，不能依赖隐式全局查询。

### P0-3：stale verdict 可用于晋升新版本

F3 分契约要求 `candidateRevision === entry.meta.version`：
[N24-F3](./n24-f3-contract.md#L39-L42)。实现却只拒绝大于当前 version 的 verdict：
[knowledge-verdicts.ts](../../src/pth/execution/knowledge-verdicts.ts#L171-L186)。现有测试名为
“不等于拒绝”，实际只测试 future revision，没有测试 stale lower revision。

**关闭条件：**Review/Verification 必须绑定不可变 candidate revision；内容、证据、Domain 或
effect 变化后旧决定失效。多 reviewer 场景不能靠每次 append 都修改 candidate version 来表达，
应把 candidate content revision 与 review-row version 分开。

### P0-4：F5 不是 transactional outbox

任务 CAS commit 完成后，dispatcher 才调用 observer：
[task-dispatcher.ts](../../src/pth/tasking/task-dispatcher.ts#L80-L85)。Refine observer 随后独立
enqueue：[refine-observer.ts](../../src/pth/runner/observers/refine-observer.ts#L50-L69)。enqueue
失败又会被 observer 隔离为日志：
[task-outcome-observers.ts](../../src/pth/tasking/task-outcome-observers.ts#L23-L33)。

所以进程在 commit 后、enqueue 前崩溃，或数据库短暂失败时，Candidate 会永久缺失。snapshot
失败也会直接 return、不入队：[refine-observer.ts](../../src/pth/runner/observers/refine-observer.ts#L41-L48)。

**关闭条件：**task outcome 与 outbox row 必须由同一个 PostgreSQL transaction/client 提交；
或保存足够的 durable outcome event，使 repair worker 可确定性补写，不能靠 post-commit callback。

### P0-5：outbox 多进程 claim 无效

`claimPending` 使用自动提交的单条 `SELECT ... FOR UPDATE SKIP LOCKED`：
[side-effect-outbox.ts](../../packages/pth-kernel-storage/src/side-effect-outbox.ts#L60-L81)。查询返回时事务已经结束，
行锁已释放；记录也没有被原子改成 processing。`complete/markFailed` 只按 key 更新，没有 claim
token、owner、lease deadline 或 status CAS：
[side-effect-outbox.ts](../../packages/pth-kernel-storage/src/side-effect-outbox.ts#L84-L100)。

两个独立 drainer 的负向探针能让同一行被处理两次。更坏的竞态是：一个 handler 已 complete，
另一个 stale handler 仍可把同一行改回 pending。

**关闭条件：**原子 `pending → processing` claim，生成 claim token/lease；complete/fail 必须携带
token 且匹配 processing；支持 lease 过期回收、availableAt/backoff、lastError 与 dead-letter。

## 4. 高优先级缺口

### P1-1：Domain 子集与 binding 不一致

delegate 接受 domains 子集，但仍原样写入父 binding：
[task-control-service.ts](../../src/pth/tasking/task-control-service.ts#L100-L117)。如果父 binding
包含 A、B，而子任务只保留 A，claim reader 会因 binding 中含 B 而丢弃整个 binding：
[task-work-item-reader.ts](../../src/pth/tasking/task-work-item-reader.ts#L47-L55)。

需要按选中 domains 重新构造 matches/primaryDomain，保留 catalog/resolver version，并增加
`publish(A,B) → delegate(A) → claim` 组合断言。

### P1-2：VerificationPlan 与 service 授权仍缺失

HTTP role gate 和 worker principal 解决了“明显匿名调用”，但没有持久 VerificationPlan 去绑定：

- required domains；
- candidate revision；
- eligible principals/roles 与 separation rule；
- execution/grant；
- evidence requirement 与 quorum。

`recordKnowledgeVerdict` 的 server opts 仍可选，service 本身没有 grant/RBAC：
[knowledge-promotion.ts](../../src/pth/execution/knowledge-promotion.ts#L24-L38)。授权不能只存在于
某一个 HTTP adapter。

### P1-3：F4 指标仍有自证空间

Evaluator 手工复制检索管线：
[pilot-evaluator.ts](../../src/pth/catalog/pilot-evaluator.ts#L111-L143)，没有通过生产端口验证
tenant/status/space/evidence injection。60 个标准问题只指向两个域各五条 core knowledge；其余
14 条即使内容和 evidence 都损坏，指标仍全部为 1.0。

另外，查询 token 零命中时过滤函数返回全部候选：
[knowledge-ranking.ts](../../src/pth/execution/knowledge-ranking.ts#L39-L60)。当前 hard negative 不含
域别名，主要测试“resolver 无域”，没有测试“已解析到域但应无答案”。

**关闭条件：**评测调用生产 Broker/Context 端口；覆盖全部 24 条知识；加入同域 no-answer、
无关内容、顺序扰动、冲突来源、跨版本、tenant/space visibility 和 holdout 题集。

### P1-4：结构化 EvidenceRef 没有贯通 worker 上下文

Seed 和 live evaluator 已读 `meta.evidence`，但生产 KnowledgeContext 仍主要映射 provenance：
[knowledge-context.ts](../../src/pth/runner/knowledge-context.ts#L169-L176)。评测验证的 evidence
结构并不等于 worker 实际收到的结构。

需要让同一 `EvidenceRef {sourceId, locator, sourceVersion, artifactHash...}` 从 DB、Broker、
Context、Candidate、VerificationPlan 到 promotion 全链保持类型一致。

### P1-5：完整测试仍报告 observer 组合故障

本次 `npm test` 虽以 exit 0 结束，但真实 batch 组合期间仍出现：

```text
observer failed: Cannot read properties of undefined (reading 'pool')
```

因此“audit/transcripts 绑定测试通过”只能证明窄单测，不足以证明生产 observer fan-out 已关闭。
需要给 observer 加名称/阶段上下文并让关键持久化 observer 失败进入可查询的 durable failure，而不是
只写 warning 后继续绿测。

## 6. 重新关闭 Gate 的最小顺序

1. **R1—revision/promotion correctness**：统一 version 语义，增加 expected-revision CAS、
   并发 verdict、promotion 后二次 mutation 与 domain-method PG 测试。
2. **R2—tenant query plane**：raw SQL 强制 tenant/status/space；补跨租户负向。
3. **R3—verification binding**：持久 VerificationPlan，service 层授权，严格 revision 绑定；
   修复 Domain subset binding。
4. **R4—true transactional outbox**：同事务 enqueue、claim lease/token、CAS complete/fail、
   timeout recovery、多进程真实 PG 测试。
5. **R5—production evaluation**：通过生产端口评测、全语料覆盖、同域拒答/冲突/跨版本/holdout，
   EvidenceRef 全链一致。
6. **R6—composition acceptance**：重跑完整 `claim → context → commit → outbox → candidate →
   verification → promotion → retrieve`，覆盖进程崩溃、并发与跨租户。

只有 R1–R6 的正向与负向证据均成立，才可把 Gate A/B/C 改回 accepted。

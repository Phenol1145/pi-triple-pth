# N16：v1.2 角色谱系大规模扩展设计

> 2026-08-18 · 概念前提：`concepts.md §0.17`（worker 优化四层次）、§0.16（任务拓扑与穿透）。
> 本文是 v1.2「实用阶段」的角色谱系扩展设计：**从 15 个 actuator 叶子扩展到 160+ 个角色**，
> 覆盖 Wikipedia 五大学科门类的完整子学科层级。
>
> 版本目标：让 PTH 成为一个**通用 AI 团队**——任何学科的专业问题都能找到对应的专职 worker。

## 0. 动机与设计原则

### 0.1 为什么需要大规模扩展

当前 15 个 actuator 叶子角色覆盖了软件开发、文档写作、信息侦察、规划验收、深度分析五类
通用能力。但对于「实用阶段」的真实业务任务，缺少学科专精：

- 一个经济学问题交给 analyst 处理，它没有经济学专业知识背景；
- 一个医学文献检索任务交给 scout，它不知道 PubMed 和临床试验数据库；
- 一个法律合同审查任务交给 acceptor，它没有法律推理框架。

**学科专精 = 领域知识 + 方法论 + 工具生态 + 术语体系**。每个学科子角色在其 prompt 中
携带该学科的专用知识框架，才能产出专业水平的结果。

### 0.2 设计原则

1. **遵循 Wikipedia 分类标准**：以 [Outline of Academic Disciplines](https://en.wikipedia.org/wiki/Outline_of_academic_disciplines)
   和中文维基 [学术领域大纲](https://zh.wikipedia.org/wiki/%E5%AD%A6%E6%9C%AF%E9%A2%86%E5%9F%9F%E5%A4%A7%E7%BA%B2)
   为分类基准，不做自定义分类体系。
2. **遵循谱系分化结构**：每个新角色有明确的 parent/child/generation 位置，遵循 0.16.1
   类型树规则——组织权逐级继承、分化按「负责的问题类型」。
3. **门类做中间层，学科做叶子**：gen=3 为五大门类（收口投递），gen=4 为学科（实际执行），
   gen=5 为子学科（深度专精）。
4. **角色定义是数据，不是代码**：`WorkerRole` 接口只需 id/tags/prompt/description/
   thinking/capabilities/actionTools/parent/generation/differentiation。新增角色
   不修改核心机制，只扩展 `builtin-roles.ts` 数据。
5. **工程与理论分立**：形式科学（数学/逻辑/CS）和自然科学（物理/化学/生物）是理论侧，
   应用科学（工程/医学/农业等）是实践侧——两者分属不同门类，不在同一分支下。

### 0.3 与既有机制的关系

| 既有机制 | 本设计的影响 |
|---------|------------|
| **任务池路由** | 新角色携带新 tags，任务池按 tags 精确匹配路由——不冲突 |
| **组织权矩阵** | 新角色挂在现有谱系下，组织权逐级继承——不冲突 |
| **0.16.4 工具面收口** | gen=3 门类角色 actionTools = `["execTs","nav","cache"]`（收口）；
  gen=4/5 学科角色可按需扩展（执行核/专项工具） |
| **batch 构成** | 新角色默认不进 batch（`PTH_WORKER_ROLES` 显式启用），避免内存爆炸 |
| **SOP** | 每个角色配一条四段式 SOP（L2 批次），遵循 W4 创建时机 |
| **知识填充** | 百科（pth-wiki）按学科门类填充术语，角色文档（role-doc）按三要素补齐 |

```
executor (gen=2)
├─ developer ─── coder
│              ├─ tester ─── debug-case-writer
│              ├─ 🆕 debugger (gen=4)     ← 根因定位/调试专精
│              └─ 🆕 reviewer (gen=4)     ← 代码/设计审查专精
├─ writer
└─ 🆕 communicator (gen=3)               ← 对外沟通/汇报/翻译

governor (gen=2)
├─ planner
├─ acceptor
└─ 🆕 coordinator (gen=3)                ← 进度追踪/跨任务协调
```

## 3. 角色定义模板

所有新角色遵循统一的 `WorkerRole` 接口。关键字段约定：

### 3.1 能力面（capabilities）

gen=4 学科角色统一使用：
```typescript
capabilities: ["fs", "memory", "readSource", "readText", "web", "python", "bash"]
```
——全量读取 + 双语言执行核 + 网络检索。gen=5 子学科继承不放缩。

gen=3 门类角色（中间层）遵循 0.16.4 收口：
```typescript
capabilities: ["fs", "memory", "readSource", "readText", "web"]
actionTools: ["execTs", "nav", "cache"]
```
——只做路由派发，不亲自执行。

### 3.2 推理档（thinking）

| 类型 | thinking | 理由 |
|------|----------|------|
| gen=3 门类 | high | 需要判断任务归属哪个子学科 |
| gen=4 学科 | high | 学科级推理需要深度 |
| gen=5 子学科 | medium | 专精领域，推理深度适度 |
| executor 新角色 | high | 调试/审查需要深度推理 |

### 3.3 模型选择

不强制指定 model（走全局默认）。planner 和 controller 系保留 pro 模型。
executor 族叶子保留 flash 模型（0.2 高低智力分层）。

### 3.4 Prompt 结构

每个角色的 prompt 遵循三要素结构：
```
你是 [角色名]——[一句话职责]。

【学科背景】（gen=4/5 专属）
- 核心知识领域：...
- 主要方法论：...
- 关键工具/数据源：...

【工作流】
- 理解任务 → 检索知识 → 分析/执行 → 产出结论

【产出格式】
- done.result 包含：...
```

## 4. 批量生成策略

### 4.1 角色定义生成

149 个角色的定义不是手写——按以下策略批量生成：

1. **门类级（gen=3）×5**：手写 prompt（含学科路由判断逻辑）
2. **学科级（gen=4）×32**：手写 prompt（含学科背景知识框架）
3. **子学科级（gen=5）×112**：模板化生成——`prompt = 父学科 prompt + 子学科专精段`

模板参数：
```typescript
interface SubDisciplineTemplate {
  id: string;
  name: string;          // 中文名
  parent: string;        // 父学科 id
  description: string;   // 一句话职责
  domainKnowledge: string; // 核心知识领域
  methodology: string;   // 主要方法论
  tools: string;         // 关键工具/数据源
  tags: string[];        // 自动从名称派生
}
```

### 4.2 注册

所有角色注册到 `builtin-roles.ts` 的 `DEFAULT_ROLES` 数组。
gen=3 门类角色同时加入 `MID_ROLES` 数组（中间层展开）。

### 4.3 测试

- 角色定义完整性测试：每个角色 id/tags/prompt/parent/generation 非空
- 谱系一致性测试：所有 parent 指向存在的角色、无循环引用
- 标签唯一性测试：无重复角色 id
- 组织权测试：父→子路径命中组织权矩阵

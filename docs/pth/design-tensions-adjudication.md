## T1 worker-index 全员注入 vs 专注度核心

- **双方依据**：0.7 核心区寸土寸金（无关清单稀释注意力）vs 0.8 锚点原则（worker-index 是路由/协作依据）。
- **代码现状**：`agent-loop.ts` L204 全员注入（2026-08-13 planner 通道）；执行族实际收到约 22 行无关清单。
- **裁决选项**：
  - **A（★）规划系注入 + 执行族 lazy**：planner / governor / controller:×5 / sensor:×4 保留 eager 注入；执行族（developer/executor/tester/writer）与信息族（scout/explorer/analyst）改为 lazy 指针（memory.query 按需展开）。与 0.8「锚点先行」一致。
  - B 全员 lazy：worker-index 彻底退出核心区，连 planner 也走查询。信息最省，但规划/裁决角色每次多一次查询往返。
  - C 保持全员注入：信息最完整，专注度代价维持现状。
- **影响面**：注入条件按 role tags 过滤 + lazy 指针渲染（小改，agent-loop.ts 一处）。

## T2 代码缺省 eager vs 锚点先行原则

- **双方依据**：0.8 锚点先行（默认只给锚点）vs 现有 agent-loop 缺省 eager（部署层 compose 已设 lazy，但裸部署回落 eager 全文）。
- **代码现状**：`agent-loop.ts` L164/L420 `PTH_AGENT_MODE` 缺省为 eager；docker-compose 已覆盖为 lazy——**缺省与原则相反，靠部署层兜底**。
- **裁决选项**：
  - **A（★）缺省改 lazy**：代码缺省 lazy，显式 eager 白名单（稳定高频、缓存价值高的角色——如 planner）。原则落到代码层而非部署层。
  - B 保持 eager 缺省：现状，风险在"无 compose 部署"场景。
  - C auto 按模型智力映射（flash→lazy / pro→eager）：符合 0.2 分层，但映射表尚不存在，需先设计。
- **影响面**：改两处缺省值 + 编译期验证（小改）。

## T3 pick_tools 动态工具面 vs 缓存命中率

- **双方依据**：pick_tools 收缩工具面保专注度（0.7.1）vs 工具列表变动 → 前缀变动 → token 缓存失效（0.7.2 已承认）。
- **代码现状**：pick_tools 生效即重置工具面（空间切换重置、空数组恢复默认）；缓存命中链路 llm-fn → scorecard cacheRead 已闭环——**但无"何时值得牺牲缓存"的判据**。
- **裁决选项**：
  - **A（★）条件化启用**：任务剩余 maxSteps 余量充足（如 ≥10 步）且任务为探索/执行型时允许 pick_tools；短任务与高频重复型任务（统计/验收）禁用——缓存优先。阈值走 perf-params（硬边界原则，不硬编码）。
  - B 现状承认：动态面随时可用，缓存牺牲计入成本（不新增判据）。
  - C 长前缀任务一律禁用 pick_tools：简单，但一刀切会伤到长任务恰恰最需要收缩工具面的场景。
- **影响面**：agent-loop 加一个条件分支 + perf-params 暴露阈值（中改）。

## T4 JIT 自动 apply vs 审批面人工闸门

- **双方依据**：0.6.1「控制量不自动生效」（人在回路）vs JIT 内环需要分钟级闭环（optimizer-apply 现状自动落）。
- **代码现状**：建议一律 draft（worker 面无自批权）；apply 走系统通道主进程直写 store；2026-08-13 已加 deopt 基线快照与回滚。**但 apply 本身无分层——可逆微调与不可逆大变同一通道。**
- **裁决选项**：
  - **A（★）分层闸门**：可逆微调（提示资产/热参数/工具面调整）自动 apply + deopt 回滚兜底；不可逆大变（角色分化、代码层、删除类）必须人工闸门（审批面 A/C 已有）。与 §4 原则 6「可逆微调 JIT 自动+deopt 制动」完全一致。
  - B 全人工：最安全，但 JIT 内环退化为"建议箱"，分钟级闭环失效。
  - C 全自动：闭环最快，但删除/分化类失控风险高，违背 0.6.1。
- **影响面**：optimizer-apply 按 suggestion 类型分流（中改——类型学已存在：optimizer-suggestion / differentiation）。
- **我的选择**：___

## T5 负结果收敛 N=5 终止 vs 合法多探测

- **双方依据**：死循环制动（0.6 稳定性，N=3 引导/N=5 终止）vs scout 侦察类任务合法查多源（同族同目标连查 ≠ 死循环）。
- **代码现状**：agent-loop.ts 窗口 6 步，按"同工具族 + 同目标 + 连续负结果"判定；目标提取含语义维度、路径模式化——**但 scout 多源探测与无效重试在特征上难以区分**。
- **裁决选项**：
  - **A（★）侦察类豁免终止**：scout / explorer 保留 N=3 引导（提示换策略），豁免 N=5 强制终止（以 maxSteps 兜底）；其余角色维持 N=5。区分依据：role tags（recon/investigate/explore）。
  - B 目标判定加多样性：不同查询参数/不同源视为不同目标——降低误判，但削弱对"换汤不换药"循环的制动。
  - C 现状观察：保持现行逻辑，出现误杀案例再调（最省事，代价是 scout 任务可能被误终止）。
- **影响面**：收敛检查加角色 tag 判断（小改）。

## T6 空间持久化 vs 空间治理

- **双方依据**：0.9.2 空间持久化（重启恢复）vs 临时空间永久化 → 治理负担单调增长。
- **代码现状**：space-registry.ts 无生命周期概念（无 persist/archive/TTL 关键字）——所有空间一律保留。
- **裁决选项**：
  - **A（★）三态生命周期**：临时（会话/任务级，TTL 自动回收）/ 持久（显式标记，重启恢复）/ 归档（治理动作，压缩后进归档区）。治理 v2 的裁剪落在"临时→回收"与"持久→归档"两步，与持久化不再冲突。
  - B 现状 + 治理 v2 后补：先接受增长，治理 v2 设计时一并处理（时间换复杂度）。
  - C 取消临时空间持久化：与 0.9.2 重启恢复机制直接冲突，仅列作对比项，不推荐。
- **影响面**：space-registry 加生命周期字段 + TTL 回收 + 归档命令（中改）。

## T7 记忆空间单调增长 vs 有界上下文

- **双方依据**：0.9.4 上下文有界（治理专注度）vs 记忆库无限增长（存储与检索质量双降）。
- **代码现状**：sensor:memory（观测）与 controller:memory（裁决，prompt 已含归档/合并/清理策略）角色已存在；`manage.memory.archive` 为 draft 提案流——**归档工具未实装，闭环缺"执行"一环**。
- **裁决选项**：
  - **A（★）实装归档闭环**：实装 manage.memory.archive 工具（draft → 监督层批准 → 执行），controller:memory 定期任务触发（阈值：容量/命中率/重复度）。删除类保持人工批准（与 T4 分层一致）。
  - B 仅手动归档命令：不做定期自动，人工按需清理（省实现，治理靠人）。
  - C 暂缓：记忆规模未到痛点，先标记债务（最快，但检索质量会先于容量疼痛——低命中条目稀释检索）。
- **影响面**：memory 工具族补 archive + 定期任务调度（中改）。

## T8 能力文档格式 vs 描述三要素锚点标准

- **双方依据**：capability-index 现状清单式（"- perf: …"逐条罗列）vs 0.8.2 锚点三要素（【场景锚点】/ 何时用 / 效果预告）——两套描述标准并存。
- **代码现状**：prompt-docs.ts 分节约定（## 基础/## memory/## fs/…）承担裁剪；agent-tools 场景化描述已按三要素改——**能力文档未同步**。
- **裁决选项**：
  - **A（★）统一到锚点标准**：capability-index 逐条改三要素锚点，保留分节裁剪（裁剪是结构、锚点是格式，两者正交）。与 §8.2 债务「术语统一」合并执行。
  - B 两套并存划界：能力文档保持清单式（密度高），三要素仅限 LLM 工具 description——但 0.8.2 已把"描述清楚何时读"定为通用标准，并存会继续稀释专注度。
  - C 回退清单式：放弃三要素，历史成本白付。
- **影响面**：capability-index 文案重写 + 注入侧校验（中改，纯文档化）。

## T9 渐进降输入 vs 任务理解质量（📌 边界条件，非矛盾）

- **双方依据**：任务文本只写核心意图（上下文靠 PTH 内部状态自取）vs "最短指令"存在下界——核心意图必须完整到可分派。
- **现状**：提交侧（pth-cli / PTL）无意图完整性校验；文本不足时任务在池内空转或被错误路由。
- **裁决选项**：
  - **A（★）确认为边界条件 + 提交侧校验**：正式确认为边界条件（分派下界 = 核心意图完整）;提交侧加最小校验（必填字段 + 可路由提示——缺意图时即时反馈而非进池空转）。T9 从"待裁决"转"已确认"。
  - B 仅文档确认：不加校验，依赖提交者自觉。
  - C 接收侧补全：PTH 端自动补全意图——不可行（补全即推测，违背最小信息原则）。
- **影响面**：pth-cli submit 前置校验（小改）+ concepts.md 状态改 📌。

## T10 环间同对象仲裁（JIT 环 vs 控制环）

- **双方依据**：JIT 内环（分钟级）与控制环（批次/小时级）可作用于同一角色/空间——无写入仲裁，慢环裁决时快环可能已改同一对象。
- **代码现状**：optimizer-loop / controller 角色均无并发仲裁机制；时间尺度分离（0.6.3）是唯一隐性隔离。
- **裁决选项**：
  - A 目标级写锁：proposal 目标键（角色/空间）互斥——内环持有即快环优先，慢环冲突时降级回 draft 待下轮（符合 0.6.3 环间不互相干扰）。
  - B 时间尺度声明隔离：文档声明"慢环裁决窗口内快环暂停 apply"——实现简单，但会拖慢内环。
  - **C（★）暂缓观察**：优先级最低，暂无实际冲突案例——先标记，出现同对象冲突实例（obs 可观测）后再按 A 实装。
- **影响面**：暂缓零成本；实装 A 为小改（proposal 写入互斥）。

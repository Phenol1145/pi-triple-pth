# N16 v1.2 角色扩展问题反馈评审

> 日期：2026-08-17  
> 状态：已闭环——评审结论已吸收进组合设计稿，v1.2 验收通过（2026-08）  
> 评审对象：[N16：v1.2 角色谱系大规模扩展设计](./n16-v1.2-role-expansion.md)  
> 配套改进方案：[角色 × 学科域组合与 PTH Knowledge 设计](./n16-v1.2-role-domain-composition-design.md)  
> 事实源：当前工作区的 N16 角色表、PTH 任务/角色/目录/记忆运行时代码与框架契约。

## 1. 执行结论

N16 的方向正确：把 researcher 族按“门类 → 学科 → 子学科”分层，并把门类角色限制为路由者、学科与子学科角色定位为专业执行者，是比继续扩张通用 `analyst` 更清晰的组织模型。角色数据化、能力面收口、SOP 与知识填充分期，也都值得保留。

但当前文档不能直接进入既有 V1–V5 实施。角色表的真实规模是 **188 个新角色**，不是 149 个；更关键的是，当前运行时会在默认配置下把 `DEFAULT_ROLES` 全部展开为常驻 worker，显式配置也会把未列角色补成 1 份。若按 N16 注册，空配置会尝试展开 188 个新角色，显式配置则会触发 32-worker 上限。gen=3 同时放入 `DEFAULT_ROLES` 与 `MID_ROLES` 还会令 catalog 因重复 id 在启动期 fail-closed。

知识侧同样尚未形成可验证闭环：当前检索是精确锚点并集且无相关性排序；记忆 store 没有真正按 tenant 过滤；来源、证据和修订历史不是强制字段；refiner 会把任务洞察直接写成 `official`，且缺失空间元数据时按 `meta + public` 解释；常规检索也可能返回 archived 条目，却不会自动累计命中。把 188 个 prompt 和百科文本批量写入，只会扩大不可审计知识的表面积。

建议处置为：**保留 184 个 researcher 节点作为学科目录种子，不将它们静态物化为 worker；先完成知识正确性加固，再以编程语言官方文档与材料科学开放数据库做端到端试点，达标后才扩展领域覆盖。** 四个非 researcher 角色仍可按工作承诺独立评审，不与学科目录批量绑定。

## 2. 值得保留的设计

1. **专业领域的三级谱系。** gen=3/4/5 整理出的“门类 → 学科 → 子学科”是有价值的目录种子；应保留层级内容，但将其解释为 Discipline Catalog，而不是 184 种工作身份。这一分层原则在 [N16 §0.2](./n16-v1.2-role-expansion.md#L23-L36) 与 [concepts §0.18.2](./concepts.md#L785-L797) 中一致。
2. **门类层只导航、不亲自执行。** N16 对 gen=3 的约束说明“分类导航”和“任务执行”应分离，见 [N16 §3.1](./n16-v1.2-role-expansion.md#L354-L367)。改进后由 Discipline Resolver 使用 category 节点导航，不为它常驻 worker。
3. **定义数据化。** `WorkerRole` 已具备 parent、generation、capabilities、actionTools、thinking 等表达面，见 [worker-cluster.ts](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L6-L47)；学科也应由单一、机器可校验的 manifest 生成，但进入独立的 domain schema，而不是复用 `WorkerRole`。
4. **专业框架四要素。** “领域知识 + 方法论 + 工具生态 + 术语体系”比只写一段角色人设更可操作，见 [N16 §0.1](./n16-v1.2-role-expansion.md#L11-L21)。后续应把其中稳定方法放在 role/SOP，把可变事实放入可验证知识库。
5. **新增非 researcher 角色的职责边界。** debugger、reviewer、communicator、coordinator 分别补足根因分析、质量审查、对外表达和状态协调，角色本身有价值，见 [N16 §2.6](./n16-v1.2-role-expansion.md#L335-L346)。
6. **SOP 与知识填充分期。** 先建立可执行角色，再补 SOP 与语料的顺序合理；问题在于当前数量、质量门槛和治理链未定义，而不是应取消这两类产物。

## 3. 原方案物化基数复核

本表按 N16 §2 的每一行角色定义重新计数，不采用各小节标题中的旧数字。

| generation | researcher 侧 | 非 researcher 侧 | 实际新增数 | 组成 |
|---|---:|---:|---:|---|
| gen=3 | 5 | 2 | **7** | 五大门类 + communicator + coordinator |
| gen=4 | 32 | 2 | **34** | 32 个学科 + debugger + reviewer |
| gen=5 | 147 | 0 | **147** | 五大门类下全部子学科 |
| **合计** | **184** | **4** | **188** | `5 + 32 + 147 = 184`；`184 + 4 = 188` |

gen=5 的 147 个角色由五个分支相加得到：形式科学 26、自然科学 29、社会科学 37、人文学科 22、应用科学 33。对应明细见 [N16 §2.1–§2.5](./n16-v1.2-role-expansion.md#L126-L333)。非 researcher 表实际只有 4 行，见 [N16 §2.6](./n16-v1.2-role-expansion.md#L335-L342)。

文档当前存在三套互不一致的数字：

- 标题目标写“160+”，见 [文档开头](./n16-v1.2-role-expansion.md#L1-L7)；
- 生成策略、分期和验收写“149 个角色 / 112 个子学科”，见 [§4.1](./n16-v1.2-role-expansion.md#L403-L411)、[§5](./n16-v1.2-role-expansion.md#L441-L450) 与 [§7](./n16-v1.2-role-expansion.md#L465-L472)；
- 即使采用文档声称的 112 个子学科，算术也应为 `5 + 32 + 112 + 4 = 153`，不是 149；按角色表真实内容则为 `5 + 32 + 147 + 4 = 188`。

**结论：** 所有规模、工期、SOP 数、batch 预算和验收分母必须统一改为从角色清单自动生成，不能继续手工维护总数。

## 4. P0：阻止实施的运行时问题

### P0-1 `DEFAULT_ROLES` 与“显式启用”语义相反

- **证据：** N16 要求所有新角色进入 `DEFAULT_ROLES`，同时声称新角色默认不进 batch，见 [N16 §4.2](./n16-v1.2-role-expansion.md#L427-L430) 与 [§7-5](./n16-v1.2-role-expansion.md#L465-L472)。当前 `parseRoleWeights` 在配置为空时给每个 `allWorkerRoles()` 一份，在显式配置时也把所有未列角色补成一份，见 [worker-cluster.ts](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L67-L99)。batch 启动直接展开这张表，见 [batch-process.ts](../../src/pth/bootstrap/batch-process.ts#L272-L275)。
- **影响：** 把 188 个新角色放入 `DEFAULT_ROLES` 后，不配置环境变量会全部常驻；配置少数角色也不能实现 opt-in。内存、kernel 数量和 LLM 并发都会失控。
- **建议：** 从根本上分离 Operational Role 与 Discipline。184 个 researcher 侧节点进入 Discipline Catalog，不进入 `DEFAULT_ROLES`；四个非 researcher 候选角色逐个评审。另行分离“可路由操作角色目录”和“默认常驻 worker 集”，`PTH_WORKER_ROLES` 采用“只启用列出的角色”语义，未列操作角色为 0。
- **验收检查：** 导入 184 个学科节点后，不设置 `PTH_WORKER_ROLES` 时常驻角色数与变更前一致；设置 `analyst:1,solver:1` 时只生成这两个 operational workers；学科目录仍能列出全部 184 个领域节点。

### P0-2 32-worker 上限路径使显式配置也不可用

- **证据：** `MAX_TOTAL_WORKERS=32`，显式或对象配置最终调用 `validateWeights`，总数超过 32 即抛错；但空配置分支未调用校验，见 [worker-cluster.ts](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L64-L99) 与 [validateWeights](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L175-L185)。
- **影响：** 当前有两个坏结果：空配置绕过上限并展开全量角色；显式配置因“未列角色补 1”而超过 32、启动失败。N16 没有任何可工作的 batch 配置路径。
- **建议：** 先修复 opt-in 语义，再让所有入口统一经过 `validateWeights`。上限约束的是常驻 operational worker 副本数，不是 Discipline Catalog 节点数；目录规模与执行规模必须分开计量。
- **验收检查：** 空配置、字符串配置、对象配置三条路径都经过同一验证器；catalog 含 184 个学科节点时，2 个显式 operational workers 可启动，33 个副本稳定被拒绝，错误信息报告“副本总数 33 > 32”。

### P0-3 gen=3 同时注册到 `DEFAULT_ROLES` 与 `MID_ROLES` 会重复

- **证据：** N16 要求 gen=3 同时加入两个数组，见 [N16 §4.2](./n16-v1.2-role-expansion.md#L427-L430)。`buildBuiltinCatalog` 将 `DEFAULT_ROLES` 与 `MID_ROLES` 直接拼接，见 [builtin-catalog-contributions.ts](../../src/pth/catalog/adapters/builtin-catalog-contributions.ts#L13-L28)；`CatalogBuilder` 对重复 id fail-closed，见 [catalog-builder.ts](../../src/pth/catalog/catalog-builder.ts#L25-L42)。
- **影响：** 五个门类角色一旦按文档同时加入两个数组，PTH 会在监听端口或 fork worker 前启动失败。角色目录、标签注册和组织权输入也会出现重复项。
- **建议：** 五个门类改为 Discipline Catalog 的 `level=category` 节点，只注册一次，不进入 `DEFAULT_ROLES` 或 `MID_ROLES`。每个 operational role 也只能有一个注册真相源；目录、路由和 batch 分别从正确维度派生视图。
- **验收检查：** 五个 category 节点在学科目录中各出现一次；两个 worker 数组都不含它们；重复 role/domain id 测试继续保持 fail-closed。

### P0-4 精确标签会冲突，跨学科标签无法表达

- **证据：** 当前路由把每个 tag 映射到角色集合；命中多个角色即返回冲突，见 [role-routing-policy.ts](../../src/pth/catalog/role-routing-policy.ts#L13-L44)。标签注册也拒绝跨角色同名，见 [worker-cluster.ts](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L208-L236)。现有 `analyst` 已占用 `analysis` 标签，见 [builtin-roles.ts](../../packages/pth-kernel-execution/src/execution/builtin-roles.ts#L31-L37)；N16 又定义 id=`analysis` 的数学子学科，并要求 tags 从名称派生，见 [N16 角色表](./n16-v1.2-role-expansion.md#L131-L138) 与 [模板参数](./n16-v1.2-role-expansion.md#L413-L424)。
- **影响：** 自动生成的 `analysis` 标签会在注册期冲突。即使所有单标签唯一，同时命中 `materials-science` 与 `artificial-intelligence` 也会被判定为两个路由角色，而不是跨学科任务。N16 所称“精确匹配路由——不冲突”不成立。
- **建议：** 将“唯一操作角色路由”与“多值学科识别”分离。任务只有一个 `assignedRole`，例如 `solver`；`domains` 可以同时包含 `materials-science` 与 `artificial-intelligence`。Role Routing Policy 与 Discipline Resolver 独立运行，再由系统级规划器生成主任务和辅助验证任务。
- **验收检查：** 全量导入时所有 role/domain id 唯一；旧 `analysis` route tag 与 `mathematical-analysis` domain 不冲突；同时包含两个学科域的任务可以发布，并确定一个 operational role 和至少一个绑定相关 domain 的辅助验证任务。

### P0-5 没有可执行的跨学科验证与委派拓扑

- **证据：** 委派规则默认只允许直接子类型；只有 `planner/governor` 额外获得 executor 族权限，治理 sensor/controller 不走 delegate，见 [delegation-policy.ts](../../src/pth/tasking/delegation-policy.ts#L1-L10) 与 [allowedDelegationTargets](../../src/pth/tasking/delegation-policy.ts#L54-L74)。`coordinator` 是 governor 的叶子，`reviewer` 位于 developer 下，见 [N16 §1.2](./n16-v1.2-role-expansion.md#L105-L120)；二者都不能委派 researcher 侧的领域验证者。`acceptanceRole` 目前也明确只是声明，见 [worker-cluster.ts](../../packages/pth-kernel-execution/src/execution/worker-cluster.ts#L28-L30)。成功结果直接成为 `completed`，见 [agent-task-runner.ts](../../src/pth/runner/agent-task-runner.ts#L134-L152) 与 [pg-task-repository.ts](../../src/pth/tasking/adapters/pg-task-repository.ts#L136-L168)。
- **影响：** 领域 worker 可以自报完成，但 acceptor、reviewer、coordinator 无法在现有组织权下派发独立的领域同行复核。跨学科结果更没有主审/辅审/冲突裁决流程，知识写回不能以“已验证”为前提。
- **建议：** 增加系统级 `VerificationPlan`，由主领域、辅助领域、通用 acceptor 三类验证要求组成；验证任务由受控 flow/服务发布，不依赖叶子 worker 的组织权。producer 与 verifier 必须是不同执行实例。coordinator 只跟踪状态，acceptor 检查通用交付标准；绑定相应 domain context 的 verifier 负责事实与方法复核，reviewer/tester 分别负责文档代码质量与可执行证据。
- **验收检查：** `materials-science` 生产任务可自动生成另一实例、同 domain scope 的领域复核和 acceptor 通用验收；任一复核失败时知识候选保持 draft；全部通过后才允许 memory-keeper 晋升 official；coordinator 无直接晋升权限。

## 5. P1：知识正确性与隔离缺口

### P1-1 精确锚点并集、无相关性排序

- **证据：** `retrieve` 使用 JSONB `?|`，多个 anchors 是任一命中；结果仅按 id 字典序排序，见 [memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L142-L165)。agent 启动时只注入记忆 kind 计数，不检索任务相关内容，见 [agent-loop-guards.ts](../../packages/pth-kernel-execution/src/execution/agent-loop-guards.ts#L127-L152)。
- **影响：** 同义词、上下位关系和跨语言术语无法召回；宽泛锚点会返回大量无序内容；188 个领域扩大后，模型必须自己写 SQL 并猜锚点，专业角色不等于拥有专业知识。
- **建议：** 定义结构化 `KnowledgeQuery`：tenant、space、allowedStatus、主领域、辅助领域、anchors、queryText、topK。检索至少组合精确锚点与全文相关性，并给出可解释分数和稳定 tie-break；向量召回可在试点数据证明收益后加入。
- **验收检查：** `programming-languages` 与 `materials-science` 试点各建立固定查询集；同义词和中英术语能在 top-5 命中正确条目；同输入排序稳定；每条结果返回命中原因和分数。

### P1-2 来源元数据随意，缺少不可变修订历史

- **证据：** `MemoryEntry` 仅要求通用 `meta`，`ruleRef/idempotencyKey/promotedFrom` 都是可选字段，未强制 source、citation、producer、verifier 或内容哈希，见 [memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L4-L20)。同 id 写入走 upsert，直接覆盖 content/anchors/status，只递增版本号，没有 revision 表，见 [write](../../packages/pth-memory/src/memory-store-pg.ts#L45-L91)；DDL 也只有当前态 `memory_entries`，见 [schema.ts](../../packages/pth-memory/src/schema.ts#L5-L27)。
- **影响：** 无法回答“这条结论来自哪个任务、哪些原始来源、由谁验证、旧版本说了什么”。错误知识覆盖后缺乏可审计 diff 与可靠回滚依据。
- **建议：** 对领域知识定义强制 provenance schema：sourceTaskId、producerRole、producerModel、sourceRefs、contentHash、createdAt、verificationIds、verifierRoles、prompt/role 版本。内容修订采用 append-only revision 或独立历史表，当前条目只保存活动 revision 指针。
- **验收检查：** 任一 official 条目都能反查生产任务、原始来源、全部验证结论和完整修订链；覆盖写缺少来源或验证 id 时调用即拒绝；可选择任一历史 revision 恢复并保留新审计事件。

### P1-3 memory store 的 tenant 字段没有进入读写条件

- **证据：** DDL 定义了 `tenant_id`，见 [schema.ts](../../packages/pth-memory/src/schema.ts#L5-L16)；但 `PgMemoryStore.write` 的 INSERT 不写 tenant，`get` 只按 id，`retrieve` 只按 anchors/kinds/status，见 [memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L45-L99) 与 [retrieve](../../packages/pth-memory/src/memory-store-pg.ts#L147-L165)。
- **影响：** 所有写入落到默认 tenant；任何持有 store 的调用方都能读到全局 id/anchor 结果。空间可见性不能替代 tenant 隔离，领域知识扩展会放大跨租户泄露和覆盖风险。
- **建议：** 所有 knowledge/memory port 强制接收 `TenantScope`，查询与更新必须含 tenant 条件。主键采用 `(tenant_id, id)` 或等价的租户命名空间；迁移存量默认 tenant 后再开启 fail-closed 校验。
- **验收检查：** 两个 tenant 可拥有同名知识 id；tenant A 的 get/retrieve/query 无法观察或覆盖 tenant B；缺失 tenant scope 的生产调用被拒绝；跨租户隔离测试覆盖 direct store、agent capability 与 HTTP broker。

### P1-4 refiner 直接写 official，并因 scope fallback 变成公共知识

- **证据：** refiner 将 `tool-function` 与 `task-insight` 直接写为 `official`，见 [refiner.ts](../../packages/pth-kernel-execution/src/execution/refiner.ts#L274-L311)；输入只含任务概要、snapshot、trace 和角色，没有 final result、引用或验证证据，见 [RefineInput](../../packages/pth-kernel-execution/src/execution/refiner.ts#L18-L27)。这些写入直接调用 store，不经过 worker 侧可见性盖章；缺少 `spaceScope` 的条目会被解释为 `meta + public`，见 [memory-visibility.ts](../../packages/pth-memory/src/memory-visibility.ts#L34-L40)。
- **影响：** 模型自提炼的未验证结论会立即成为所有后代空间可见的官方知识；任务结果即使没有领域复核，也会污染后续 188 个角色的检索上下文。
- **建议：** refiner 只产出带 tenant/space/provenance 的 `knowledge-proposal` draft，并接收 outcome、artifact、source refs。通过领域复核、通用验收和必要的 adversarial 审核后，由 memory-keeper 的受控 promotion service 写 official；禁止以缺失 scope 的兼容 fallback 发布新条目。
- **验收检查：** 任一普通 completed 任务不会直接增加 official 领域知识；proposal 明确携带 tenant 与 space；未验证、验证失败或缺来源的 proposal 永不晋升；新写入不存在隐式 `meta + public` 条目。

### P1-5 archived/draft 检索默认不安全，hit accounting 未接线

- **证据：** `retrieve` 只有调用方显式传 `status` 或 `excludeDrafts` 才过滤，默认返回所有状态，见 [memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L147-L165)。`skills.list` 只排除 draft，没有排除 archived，见 [capability.ts](../../src/pth/impls/kernels/capability.ts#L157-L164)。`bumpHitCount` 虽存在，但 `get/retrieve` 不调用它，生产代码也没有调用点，见 [memory-store-pg.ts](../../packages/pth-memory/src/memory-store-pg.ts#L94-L99) 与 [hit counter](../../packages/pth-memory/src/memory-store-pg.ts#L168-L173)。
- **影响：** 已归档或待审核内容可能回到 agent 上下文；`hit_count` 长期不反映实际消费，memory sensor 无法可靠判断低命中、僵尸条目或排序质量。
- **建议：** 正常知识检索默认只返回 official；draft/archived 仅治理查询可显式包含。检索服务在选定返回条目后原子累计 exposure，agent 实际加载全文时累计 consumption，并区分两类计数以避免把列表浏览当作有效使用。
- **验收检查：** 常规 agent 查询不返回 draft/archived；治理角色可显式查询它们；返回列表只增加 exposure，`get/cache.load` 增加 consumption；并发调用不丢计数，归档条目计数不再增长。

## 6. P2：可维护性与内容设计问题

### P2-1 role prompt 与领域语料混在一起

- **证据：** N16 要求每个角色在 prompt 中携带领域知识框架，并用父 prompt 加子学科专精段批量生成，见 [N16 §0.1](./n16-v1.2-role-expansion.md#L20-L21)、[§3.4](./n16-v1.2-role-expansion.md#L383-L399) 与 [§4.1](./n16-v1.2-role-expansion.md#L407-L424)。当前 role-doc 由启动期从角色定义强制写入，见 [prompt-docs.ts](../../packages/pth-kernel-execution/src/prompt-docs.ts#L126-L139)。
- **影响：** 角色职责、方法论、事实知识和数据源版本绑定到一次代码发布。147 个子学科复制父 prompt 会形成大面积重复，修正一条事实需要批量改角色定义，且无法单独记录来源与有效期。
- **建议：** prompt 只保留身份、边界、方法和检索协议；SOP 保存稳定工作流；领域事实、术语、数据源说明进入带 provenance/revision 的 corpus。role-doc 只引用 domain index 与 SOP id，不复制知识正文。
- **验收检查：** 更新 `materials-science` 的一条知识事实无需修改角色代码或任何学科 prompt；父学科方法变更只改一份共享 SOP；角色 prompt 大小受固定预算约束，并能从引用 id 定位全部外部知识。

### P2-2 “每角色一条 SOP”没有正确分母和质量指标

- **证据：** N16 要求每个角色一条 SOP，却仍计划 149 条，见 [N16 §0.3](./n16-v1.2-role-expansion.md#L38-L48)、[§5](./n16-v1.2-role-expansion.md#L441-L450) 与 [§7-6](./n16-v1.2-role-expansion.md#L465-L472)。当前系统只明确 seed developer/scout/memory-keeper 三条角色 SOP，另加四条优化 SOP，见 [prompt-docs.ts](../../packages/pth-kernel-execution/src/prompt-docs.ts#L219-L233)。
- **影响：** 按错误分母实施会至少漏 39 条新角色 SOP；纯模板复制虽然可凑数量，却不能证明 Procedure、Pitfalls、Verification 对该学科真实可用。
- **建议：** 取消“188 个节点各复制一条 SOP”的数量目标。SOP 以真实任务场景为单位建立，并通过 `roleIds[]` 与 `domainIds[]` 多对多关联；每条必须包含场景锚点、Procedure、Pitfalls、Verification、来源与评审人。覆盖率报告“冻结任务集覆盖率、复用率和回放通过率”，不能只统计文件数。
- **验收检查：** 两个试点的冻结任务都能解析到至少一条相关 SOP；同一 SOP 可被多个相邻 domain 复用；每条 Verification 可转成可执行检查或明确的人工检查；未在任务回放中证明价值的 SOP 不因目录节点存在而强制生成。

### P2-3 覆盖承诺与角色表不一致，法律动机没有 law 角色

- **证据：** 动机明确以“法律合同审查”说明 acceptor 缺少法律推理框架，见 [N16 §0.1](./n16-v1.2-role-expansion.md#L13-L21)；但完整角色表 [§2.1–§2.6](./n16-v1.2-role-expansion.md#L126-L342) 没有 law、legal-studies 或 jurisprudence 角色，`法律` 只在动机中出现一次。
- **影响：** 文档声称覆盖完整学科层级，却无法路由自己用来论证 N16 必要性的法律任务。类似遗漏若在 188 个角色批量注册后才发现，会再次修改谱系、标签、SOP 和知识语料。
- **建议：** 建立显式 coverage manifest，把目标任务族映射到门类/学科/子学科、核心数据源和验证方式。法律要么作为应用/社会科学分支正式纳入，要么从“完整覆盖”和动机示例中删除并明确非目标。
- **验收检查：** 经济、医学、法律三个动机示例都能映射到有效 domain、对应知识源与验证任务，同时只有一个 operational role；coverage manifest 对所有承诺领域无空映射；未覆盖领域在文档中明确列为非目标，不再使用“完整”描述。

## 8. 建议处置与替代实施顺序

**建议：暂停现有 V1–V5，不按“批量生成角色 → 注册 → 补 SOP → 填知识”的顺序启动。** 当前阻塞不是生成速度，而是目录、部署、路由、验证和知识治理契约尚未承载 188 个角色。

### 阶段 A：设计纠正

1. 以机器可读 manifest 复算原表：researcher 侧 184 个节点，非 researcher 侧 4 个角色候选，总计 188。
2. 将 184 个 researcher 节点转换为 `category / discipline / sub-discipline` 的 Discipline Catalog DAG；不进入角色 generation、`DEFAULT_ROLES` 或 `MID_ROLES`。
3. 四个非 researcher 角色按稳定工作承诺、组织权和工具面逐个评审，不随学科目录自动通过。
4. 分离 role catalog、domain catalog 与默认 batch composition，取消 `DEFAULT_ROLES` 的双重语义。
5. 分离唯一 `assignedRole` 与多值 `domains`；定义跨域主辅关系和解析证据。
6. 写明领域验证拓扑、角色权限和 knowledge candidate 状态机。

阶段 A 的退出条件是：完整 Discipline Catalog 可构建且无环，默认 batch 规模不变，两个显式 operational roles 可启动，重复 id/tag 与跨域双轴路由测试全部通过。

### 阶段 B：正确性加固

1. 建立 tenant-aware KnowledgeStore/Query port，所有读写 fail-closed 接收 scope。
2. 正常检索默认 official，加入相关性排序、稳定 top-k 和可解释命中原因。
3. 强制 provenance、content hash、verifier 与 append-only revision。
4. refiner 改为只写 scoped draft proposal；验证通过后由 memory-keeper 晋升。
5. 接通 archived 过滤、exposure/consumption 计数和 sensor:memory 指标。
6. 用 post-commit 事件或事务 outbox 驱动验证，不以 agent 自报完成事件作为晋升依据。

阶段 B 的退出条件是：tenant 隔离、状态过滤、来源链、历史恢复、验证失败不晋升、并发命中计数等集成测试全部通过。

### 阶段 C：两个领域试点

选择 **编程语言官方文档** 与 **材料科学开放数据库**：前者版本边界清楚，术语、API 和示例容易做可执行验证；后者能暴露多来源数值、证据定位、许可、有效时间与跨学科组合问题。每个试点只加载相关 domains、来源注册表和少量经过回放的 SOP，不为整个分支常驻 worker。

试点必须覆盖：单域检索、跨域任务、producer/verifier 分离、acceptor 通用验收、refiner draft、memory-keeper promotion、tenant 隔离、archived 排除、SOP 回放与知识修订。连续试点任务达到检索 top-k、验证通过率、错误知识零晋升、资源预算等门槛后，才能进入扩展阶段。

### 阶段 D：分批扩展

按领域逐批增加目录节点、来源与知识覆盖，每批都从 manifest 生成 domain、source、SOP 关联和评测报告。只有遥测证明某个“操作角色 × 学科组合”长期高频、稳定且有独立工具面时，才走现有分化审批固化专家角色；由真实队列需求决定是否启用及副本数。每批复用阶段 C 的端到端验收，不以“定义文件已生成”作为完成标准。

最终处置结论：**保留 N16 的学科目录内容，退回“静态物化 188 个角色”的实施序列；先设计纠正，再正确性加固，再双域试点，最后按证据扩展。**

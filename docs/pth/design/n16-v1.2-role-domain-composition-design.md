# N16 改进稿：角色 × 学科域组合与 PTH Knowledge 设计

> 日期：2026-08-17  
> 状态：已实施——v1.2 角色域组合已落地并通过验收（见 v1.2-acceptance-fix-revalidation-final.md）；本文档转为历史设计稿  
> 关系：保留 [N16 原稿](./n16-v1.2-role-expansion.md) 的学科覆盖目标，替换其“每个学科静态物化为 `WorkerRole`”的实现方式。问题证据见 [N16 问题反馈](../report/n16-v1.2-role-expansion-review.md)。

## 0. 决策摘要

v1.2 仍以“任何学科问题都能获得合适的专业知识、方法和工具”为产品目标，但专业化改为四个正交维度的任务级组合：

```text
Worker Assignment
= Operational Role       // 怎么工作：analyst / solver / reviewer …
+ Discipline Scope[]     // 懂什么：chemistry / materials-science / AI …
+ Knowledge Context      // 本任务获准读取的锚点、证据与版本
+ Capability Grant       // 本任务获准执行的动作
```

核心裁决：

1. **角色谱系只表达工作承诺与协作权**，不再复制完整学科分类。
2. **学科分类进入不可变 Discipline Catalog**，采用允许多父节点的有向无环图（DAG）。
3. **任务可绑定多个学科域**；操作角色路由与学科识别分别进行，不争用同一组 tags。
4. **prompt 只携带角色规则、学科锚点和检索纪律**，领域正文仍由 PTH Knowledge 按需提供。
5. **自动产生的知识先成为 candidate/draft**；经过领域核验、对抗审核与 memory-keeper 归一后才可晋升。
6. 第一版复用 PostgreSQL、`pth-memory` 与 grant-bound `KnowledgeBroker`；在真实评测证明需要前，不新增图数据库或向量数据库。

这与稳定词表一致：PTH 是自耦自然语言解释器；Knowledge 是拥有记忆、检索、提炼与可见性规则的能力，不是全局共享存储。[`CONTEXT.md`](../../../CONTEXT.md)

## 1. 问题、目标与边界

### 1.1 要解决的问题

当前通用角色能完成分析、探索、实现和验收，但学科任务缺少：

- 专业术语与概念索引；
- 学科方法论和证据等级；
- 权威数据源及其版本、许可和适用时间；
- 专用工具的发现方式；
- 跨学科任务的组合与交叉核验机制。

N16 原稿正确识别了这些缺口，但把“学科”直接建模为角色类型，会同时放大 batch、路由、prompt、组织权和维护成本。改进稿把学科能力放回记忆空间维度，保留角色作为动作与承诺维度。

### 1.2 设计目标

- 覆盖 N16 已整理的门类、学科和子学科，同时允许后续增删与多父归属。
- 一个任务可以组合多个学科域，而不产生角色路由冲突。
- 专业知识可追溯到来源、版本、证据定位、许可与适用时间。
- 检索上下文有界、可解释、可复现，不把学科语料常驻 prompt。
- 知识增长经过可观测、可审核、可回滚的状态机。
- 保持 `tasking / runner / execution / catalog / bootstrap / pth-memory` 的现有模块边界。
- 先用两个领域试点证明闭环，再扩大覆盖。

### 1.3 非目标

- 不以一次发布填充“全世界知识”。
- 不把 Wikipedia 分类当作唯一真理；它只是首版目录种子。
- 不在 v1.2 训练基础模型或微调 188 个模型人格。
- 不让 LLM 生成内容自动成为官方事实。
- 不以“每个角色至少一条 SOP”或“条目总数”作为专业能力的主要指标。
- 不改变 PTL/PTH 产品边界；PTL 仍只是 PTH CLI/API 的一个调用方。

## 2. 方案比较

| 方案 | 做法 | 优点 | 主要代价 | 结论 |
|---|---|---|---|---|
| A. 静态专家角色 | 每个门类、学科、子学科生成一个 `WorkerRole` | 直观；prompt 可单独定制 | batch 无法承载；单父树不支持交叉学科；大量重复 prompt/SOP；路由冲突 | 不采用 |
| **B. 角色 × 学科域组合** | 少量操作角色 + 多值 Discipline Scope + 按需 Knowledge Context | 跨学科自然；不增加常驻 worker；知识独立更新；符合动作/记忆空间分化 | 需要新增学科目录和双轴路由契约 | **采用** |
| C. 纯检索、无学科目录 | 所有任务交给通用 researcher，直接全文/向量搜索 | 初期代码最少 | 缺少方法论、证据政策、数据源选择与可解释路由；难治理 | 仅作降级路径 |

方案 B 仍允许 JIT 固化：若遥测证明某个“操作角色 × 学科组合”长期高频、稳定且有独立工具面，可通过现有分化审批生成真正的新角色。静态角色是验证后的优化产物，不是预先展开整个分类表。

## 3. 规范术语

| 术语 | 定义 | 避免 |
|---|---|---|
| **Operational Role（操作角色）** | 对任务类型、产物和协作权作出稳定承诺的角色，如 analyst、solver、reviewer | 用学科名代替工作承诺 |
| **Discipline（学科域）** | 某一知识、方法论、工具生态与术语体系的分类节点；可有多个父节点 | 把它称为 WorkerRole generation |
| **Discipline Catalog（学科目录）** | Runtime Catalog 中不可变、确定排序的学科 DAG 快照 | Wikipedia 镜像、角色树 |
| **Discipline Scope（学科作用域）** | 单个任务获准使用的一组学科节点及其祖先/相关节点 | `Profile`；该词已用于产品模块组合 |
| **Domain Knowledge（领域知识）** | 与学科域关联、带来源和适用范围的可检索知识 | 泛称“世界知识” |
| **Knowledge Candidate（知识候选）** | 尚未完成核验、不得作为官方依据的提炼结果 | 自动 official 的 task-insight |
| **Knowledge Context（知识上下文）** | 运行前为单个任务构造的有界、版本化证据包 | 整个领域语料、常驻 prompt |
| **PTH Skill** | 数据库中的四段式程序知识/SOP | 与 PTL template skill 混称 |
| **Task Episode（任务经历）** | 以 tenant/task/lineage/role/space 为键的执行记录及产物引用 | 绑定短命 worker 进程的“个人记忆” |

学科层级字段使用 `level` 或 `depth`，不使用 `generation`。`generation` 保留给真实角色谱系，避免两个不同继承关系共用一个词。

## 4. 总体架构与模块所有权

```text
External caller
      │
      ▼
Task Control ── role intent ───────▶ Role Routing Policy
      │
      └── subject signals ─────────▶ Discipline Resolver
                                         │
                                         ▼
                              TaskWorkItem(role + domains[])
                                         │ claim/lease
                                         ▼
AgentTaskRunner ── KnowledgeContextProvider ──▶ PTH Knowledge
      │                         │                 ├─ source/evidence
      │                         │                 ├─ wiki/domain/skill
      │                         │                 └─ task insight/log
      │                         ▼
      └────────────────▶ bounded KnowledgeContext
                                         │
                                         ▼
                                Agentic JIT execution
                                         │
                              committed outcome + evidence
                                         ▼
 Candidate → domain verdict → adversarial verdict → promotion
```

### 4.1 `contracts/`

拥有跨模块 JSON DTO：

- `DomainId`、`DomainBinding`；
- `KnowledgeContextRef`；
- 扩展后的 `TaskWorkItem`；
- candidate/verdict/promotion 的结构校验器。

本层不导入 PostgreSQL、模型 SDK、Fastify 或 `pth-memory` 实现。

### 4.2 `catalog/`

Runtime Catalog 继续拥有使用期不可变定义，并新增学科目录快照：

- 校验 ID、父节点、无环、多语言别名和确定排序；
- 提供 `get / ancestors / descendants / resolveAlias`；
- 不存放百科正文、证据或动态检索结果；
- 不把学科节点注入 `DEFAULT_ROLES`、`MID_ROLES`。

### 4.3 PTH Knowledge / `packages/pth-memory`

拥有：

- 知识条目、来源、证据、版本和可见性规则；
- candidate 写入与状态转换；
- 精确锚点检索以及后续可替换的排序实现；
- 领域、租户、空间、状态、时间范围过滤；
- 审核后晋升、归档与历史读取。

首版新增窄接口 `KnowledgeRepository` 与 `KnowledgeIngestor`，内部仍可委派现有 `PgMemoryStore`。调用方不直接拼写无约束 `kind/meta` 来创建官方知识。

### 4.4 `tasking/`

Task Control 仍拥有任务状态。它只保存已解析的 role/domain 绑定，不执行检索。领域识别失败可保留空 `domains` 并路由到通用 researcher；不得为了获得知识而伪造新角色。

### 4.5 `runner/`

`AgentTaskRunner.run` 在 claim 成功、kernel reset 完成后调用 `KnowledgeContextProvider`：

- 输入包含签名 lease、tenant、workspace、role、domains 和任务正文；
- 输出是有大小上限和版本摘要的 `KnowledgeContext`；
- 检索失败时记录降级原因，任务仍可通过现有按需查询继续执行；
- context 只属于本次运行，不进入全局 prompt 资产。

### 4.6 `execution/`

现有 grant-bound `KnowledgeBroker` 是执行期读取的权威缝：

- scope 只来自签名 grant；
- 增加 tenant/domain/status/time 约束；
- 对 worker 暴露 `search/get` 等窄能力，不把任意 SQL 作为未来主要知识 API；
- 写入、审核和晋升不通过只读 broker 偷渡。

### 4.7 `bootstrap/`

作为唯一组合根装配：

- Discipline Catalog；
- Discipline Resolver；
- Knowledge Context Provider；
- Knowledge Repository/Ingestor；
- candidate 审核与晋升服务。

严格扩展仍只贡献宿主已支持的声明，不绕过公开端口直接操作 store。

## 5. 最小数据契约

下列形状表达边界，不预先规定最终文件布局：

```typescript
type DomainId = string;

interface DomainDefinition {
  id: DomainId;
  names: Record<string, string>;       // zh-CN / en 等
  aliases: string[];
  parents: DomainId[];                 // 允许多父；整体必须无环
  level: "category" | "discipline" | "sub-discipline";
  description: string;
  methodAnchors: string[];
  sourceRegistryIds: string[];
  toolAnchors: string[];
}

interface DomainBinding {
  matches: Array<{
    domainId: DomainId;
    confidence: number;
    evidence: string[];                // 来自标题/正文/显式调用方字段的信号
  }>;
  primaryDomain?: DomainId;            // 仅用于排序/规划；不排除辅助领域
  catalogVersion: string;
  resolverVersion: string;
}
```

任务契约采用双轴：

```typescript
interface TaskWorkItem {
  // 现有字段保持
  assignedRole: string;                // 工作方式
  domains: readonly DomainId[];        // 知识范围，可为空或多值
  domainBinding?: DomainBinding;
}
```

若同时存在 `domains` 与 `domainBinding`，前者必须等于后者 `matches[].domainId` 去重后的确定排序结果；合同验证器拒绝二者不一致，避免路由字段和解释证据发生漂移。

来源和证据必须结构化：

```typescript
interface KnowledgeSource {
  id: string;
  authority: string;
  uri: string;
  version?: string;
  retrievedAt: string;
  license?: string;
  contentHash: string;
}

interface EvidenceRef {
  sourceId: string;
  locator: string;                     // 页码、章节、数据集行、API series id 等
  excerptHash?: string;
}

interface KnowledgeCandidate {
  id: string;
  tenantId: string;
  space: string;
  domains: DomainId[];
  kind: "domain-fact" | "domain-method" | "task-insight" | "skill";
  content: string;
  evidence: EvidenceRef[];
  validTime?: { from?: string; to?: string };
  createdFrom: { taskId: string; lineageId?: string; roleId: string };
  status: "draft";
}
```

运行前上下文必须有界并可复现：

```typescript
interface KnowledgeContext {
  id: string;
  catalogVersion: string;
  queryFingerprint: string;
  domains: DomainId[];
  entries: Array<{
    entryId: string;
    version: number;
    anchor: string;
    summary: string;
    evidence: EvidenceRef[];
  }>;
  omitted: { count: number; reason: string };
}
```

首版可把这些字段规范化存入 `MemoryEntry.meta`，但写入只能经过验证 facade；当查询与约束证明 JSONB 成为瓶颈时，再迁移独立表。

## 6. 路由与检索流程

### 6.1 双轴入口解析

1. Role Routing 根据任务意图选择工作方式，例如 analysis → analyst、closed-solve → solver。
2. Discipline Resolver 从调用方显式 domains、标题、正文和受信模板中产生多标签 `DomainBinding`。
3. 显式 domain 仍需 Catalog 校验；未知 ID fail-closed，文本推断结果可为空。
4. 多学科不是冲突：`domains` 是集合；只有多个互斥操作角色同时命中才是 role conflict。
5. `tags` 在迁移期保留，但 role tags 与 domain IDs 使用不同命名空间和字段。

### 6.2 运行前上下文构造

`KnowledgeContextProvider` 按以下顺序取数：

1. tenant + grant.space 可见性；
2. `status=official` 且未归档；
3. domain 直接节点、必要祖先与明确关联节点；
4. 任务查询与方法/来源/工具锚点；
5. 证据完整度、新鲜度、来源等级和任务相关性排序；
6. 在字符/token 预算内选择条目，记录省略原因和版本。

无证据的条目不能进入“事实”上下文；可作为探索线索时必须显式标为 unverified hint。

### 6.3 执行期按需展开

worker 先消费轻量 Knowledge Context；遇到具体问题再通过 KnowledgeBroker：

- `knowledge.search(query, domains, kinds, asOf, limit)`；
- `knowledge.get(entryId, version?)`；
- `skills.list/get` 继续用于程序知识的两级展开。

原始 SQL 保留为受控诊断能力，不作为领域 worker 的默认检索协议。

## 7. 知识增长与验证状态机

```text
committed TaskOutcome
      │
      ▼
candidate extraction (durable)
      │ status=draft + evidence + scope
      ▼
domain verification
      │ pass / reject / needs-evidence
      ▼
adversarial verification
      │ poisoning / injection / policy / shortcut
      ▼
memory-keeper canonicalization
      │ dedupe / aliases / version / supersedes
      ▼
KnowledgePromotionService (idempotent)
      │
      ├─ official + index refresh event
      └─ rejected/archive + reasons
```

规则：

- candidate 必须在任务 CAS commit 后创建；不得使用 pre-commit `task.done` 作为晋升依据。
- Refiner 获得最终 result、artifacts、引用、trace、role、domains 和 scope，而非只看 kernel snapshot。
- 后台工作必须可恢复；队列满不能静默丢失 candidate。
- 领域核验由相关学科 worker 或受信规则完成；生产者不能核验自己的 candidate。
- `controller:adversarial` 检查投毒、prompt injection、治理绕过与不可验证声明，不代替学科真实性判断。
- acceptor 检查证据完整性和交付条件，不单独判断医学、法律等领域真伪。
- memory-keeper 负责归一、去重、索引、晋升、归档，不负责发明事实。
- 所有晋升都必须幂等，并保留旧版本和 verdict 链。

## 8. 跨学科场景

任务：“用图神经网络筛选固态电解质候选，并说明结论的物理化学依据。”

```text
assignedRole: solver
domains:
  - artificial-intelligence
  - materials-science
  - physical-chemistry
```

执行方式：

1. Role Router 只选择 solver，不在三个学科角色之间冲突。
2. Discipline Resolver 绑定三个领域，并保留各自置信度与文本信号。
3. Knowledge Context 同时提供材料数据库说明、晶体/离子输运概念、图模型方法和证据来源。
4. solver 可把数据源调查、模型分析和物理化学解释投递为正交子任务。
5. 产出的新结论至少由材料/物理化学领域核验，模型代码或计算结果再由 tester/acceptor 验证。
6. 只有带数据集版本、计算参数与证据定位的结论才能进入 candidate 流。

若这种组合长期高频且独立工具面稳定，分化系统可提议 `materials-informatics-solver`；未达到证据阈值前不固化。

## 9. N16 内容的迁移映射

| N16 原内容 | 改进后落点 |
|---|---|
| 五大门类、学科、子学科清单 | `DomainDefinition` 数据；由生成器复算数量，不手写总数 |
| gen=3/4/5 | `level=category/discipline/sub-discipline`；不占角色 generation |
| 学科 parent | `parents[]`，允许交叉学科多父归属 |
| 学科 prompt | 学科 description、方法锚点、来源目录、工具锚点；正文不进 prompt |
| gen=3 门类路由 | Discipline Resolver 的目录导航；不需要常驻 worker |
| debugger/reviewer/communicator/coordinator | 仍是候选 `WorkerRole`，按工作承诺独立评审 |
| 每角色一条 SOP | 按真实任务场景建立 PTH Skill，并用 role/domain 关联；允许一对多与多对多 |
| pth-wiki 批量 seed | 两领域 pilot 的受控 Knowledge Ingestor；要求来源/版本/许可/证据 |
| role-doc 三要素 | 操作角色保留；学科改用 Discipline Index 三要素 |
| `DEFAULT_ROLES` / `MID_ROLES` 注册 | 学科不进入这两个数组；进入 Runtime Catalog 的 domains 集合 |

N16 原清单是目录输入，不再决定 worker 数量。这样可以保留已投入的学科整理工作，又不把分类规模放大为进程、prompt 与组织权规模。

## 10. 分期与原 V1–V5 调整

### Phase 0：设计纠偏

- 冻结原 V1–V5 的角色批量生成。
- 统一清单实际数量，去掉手写总数作为事实源。
- 在稳定词表中明确 Operational Role、Discipline、Discipline Scope、Knowledge Candidate。

验收：概念、设计、车道三处只引用生成器输出的数量；角色树与学科 DAG 不再共用 generation/parent 语义。

### Phase 1：Knowledge 正确性加固

- 所有 store 操作强制 tenant 条件。
- Refiner/candidate 写入强制 spaceScope。
- 官方知识要求结构化 source/evidence/version/license。
- archived 默认不参与普通检索；读取自动记 hit 或取消基于 hit 的治理决策。
- 建立不可覆盖的版本历史或等价 append-only 证据记录。

验收：真实 PostgreSQL 测试覆盖跨租户隔离、空间隔离、旧版本读取、归档排除和并发写入。

### Phase 2：学科目录与双轴任务契约

- 把 N16 清单转换为可校验的 DomainDefinition 数据。
- Catalog 支持 domains 快照与 DAG 查询。
- TaskWorkItem 增加 `domains`，Role Routing 与 Discipline Resolver 分离。

验收：增加全部学科节点不会改变默认 batch worker 数；跨学科输入得到一个 role 和多个 domains。

### Phase 3：有界检索上下文

- 在 runner 接入 KnowledgeContextProvider。
- 扩充 KnowledgeBroker 的窄 search/get 能力。
- 建立来源等级、证据完整度、新鲜度与相关性排序。

验收：相同 catalog/data 版本和任务产生相同 query fingerprint 与 context；超预算时有确定截断和省略说明。

### Phase 4：候选—验证—晋升闭环

- Refiner 只产出 draft candidate。
- 接入领域 verdict、对抗 verdict、memory-keeper 归一和幂等晋升。
- 使用可恢复的 post-commit 队列与事件。

验收：任何缺失 evidence 或 verdict 的 candidate 都不能变为 official；生产者自审被拒绝。

### Phase 5：两个领域试点

试点 A：编程语言官方文档；版本明确、术语和 API 容易验证。  
试点 B：材料科学开放数据库；能够验证多来源、数值属性、许可和跨学科组合。

每个试点建立固定评测集，至少覆盖：概念解释、方法选择、数据查询、跨版本差异、冲突来源和跨学科任务。

### Phase 6：基于证据扩展

只有试点达到验收阈值后才批量导入其他领域。是否增加语义/向量检索、独立图结构或固化专家角色，由真实失败数据决定。

## 11. 风险与护栏

| 风险 | 护栏 |
|---|---|
| 学科目录再次变成单父树 | `parents[]` + DAG 无环校验 + 跨学科测试集 |
| prompt 膨胀 | 只注入 role + domain anchors；Knowledge Context 有硬预算 |
| 来源投毒或提示注入 | 原文与指令分离；adversarial verdict；来源 allow/deny policy |
| LLM 自我确认 | 生产者与 verifier 身份分离；candidate 默认 draft |
| 知识过期 | source version + validTime + retrievedAt；as-of 查询 |
| 跨租户泄漏 | repository 每次读写绑定 tenant；真实 PG 负向测试 |
| 隐性丢失提炼任务 | durable post-commit 队列；重放/idempotency key |
| 大量低质 SOP | 以任务成功率、复用率、验证通过率衡量，不以角色覆盖计数衡量 |
| 过早增加基础设施 | PostgreSQL 首版；以查询延迟与相关性评测作为升级触发条件 |

## 12. 可量化验收标准

### 12.1 结构与运行时

- Discipline Catalog 所有 parent 存在、无环，且至少一个测试节点具有多父归属。
- 导入完整学科目录后，`DEFAULT_ROLES` 数量与默认 batch worker 数不增加。
- Catalog 构建无重复 role/domain ID，输出顺序确定。
- 30 个跨学科样例均产生恰好一个 operational role，并允许 2 个以上 domains。

### 12.2 知识正确性

- official 领域条目 100% 具有 source、contentHash、retrievedAt、evidence locator。
- 版本化来源更新后仍可按旧版本或 `asOf` 重放历史上下文。
- 跨租户、不可见空间、archived 和未核验 candidate 的负向检索测试全部拒绝或排除。
- candidate 未取得 domain verdict 与 adversarial verdict 时，晋升调用稳定失败。

### 12.3 检索质量与成本

- 两个试点各至少 30 个冻结问题；正确领域 recall@3 不低于 90%。
- 需要权威事实的问题，返回上下文的证据覆盖率不低于 95%。
- Knowledge Context 不超过配置预算，且每次截断均返回 omitted 数量与原因。
- 相同输入与版本的 query fingerprint、选中条目 ID 和顺序可复现。

### 12.4 闭环质量

- committed outcome 才能创建 candidate；CAS 未提交任务产生 0 条 candidate。
- 队列重启后 candidate extraction 可恢复且不重复晋升。
- 生产者不能作为自己的唯一领域 verifier。
- 每次 official 晋升都能反查 task lineage、证据、两个 verdict 和执行人/服务。

## 13. 实施前裁决

本提案批准后，下一步只编写实施计划，不直接批量生成角色或知识。实施计划必须先覆盖 Phase 1 的正确性加固，再进入学科目录和两领域试点；原 N16 V1–V5 不按现有顺序启动。
